# OSS Candidate Decision Matrix v1 — Professional Survey Parser Support Utilities

## Scope and Non-Authority Boundary

This decision matrix evaluates open-source candidates for future SolarPro utility adapters after the Professional Site Survey Parser V1, read-only readiness report, and expanded fixture hardening work. This is an audit and planning artifact only. No package is integrated by this report, no SolarPro geometry authority is replaced, no CAD solver is invoked, no canonical geometry is persisted as production authority, and no parser output is promoted to engineering, NEC, BOM, permit, or production CAD authority.

SolarPro remains the source of truth. Any future OSS use must be isolated behind a narrow adapter that accepts SolarPro-owned DTOs, returns versioned non-authoritative review artifacts, records deterministic hashes, and is covered by fixtures/golden tests before use in any operator-facing preview.

## Evidence Used

This matrix is based on the existing `oss-infrastructure-audit-v1.md` report plus direct npm metadata extraction for package name, version, license, modified timestamp, description, and repository URL. The metadata was collected during this phase with `npm view` and was not inferred.

## Decision Scale

`Use now` means safe to consider for a tightly scoped adapter spike in the next phase, not production authority. `Use later` means technically useful but should wait for prerequisite hardening, benchmarks, legal review, or runtime isolation. `Reject for now` means not suitable for the immediate adapter phase because of authority risk, scope, licensing complexity, runtime complexity, or insufficient near-term value.

## Category Conclusions

Polygon validation and topology utilities are the best match for the next safe adapter phase because the expanded survey fixtures exposed concrete roof polygon and geometry-readiness concerns, including self-intersection handling, invalid/zero-area polygons, duplicated roof planes, mixed units, and the need to avoid false CAD-preview promotion. `polygon-clipping` is the strongest immediate candidate because it is focused, MIT-licensed, Node-suitable, and can be isolated behind a non-authoritative adapter without changing the parser’s authority model.

Geometry clipping and intersection helpers are useful, but they must remain cross-checks and preview utilities. SolarPro should keep native validity checks as the authoritative test oracle until an explicit authority-promotion design exists. `@turf/turf` is useful for geospatial/map-facing work but should not be the first parser-hardening adapter because geodesic GeoJSON semantics differ from SolarPro’s local roof-plane XY geometry.

DXF/SVG utilities are valuable for later review artifacts, but they are not a parser-readiness dependency. The first drawing-related work should wait until canonical review geometry and preview export requirements are stable. `dxf-writer` looks safer than `makerjs` for minimal DXF output because it is narrower, but neither should be used for geometry authority.

OCR and CV tools are promising for document-derived survey evidence, but they should not be first in this phase because the parser’s document-derived fixture currently needs provenance and confidence hardening more than new extraction engines. Existing `sharp`, `tesseract.js`, and `pdf-parse` should be wrapped and tested before adding heavier CV dependencies.

Spatial indexing is low-risk and likely useful for future snapping/obstruction lookup. However, it does not address the immediate parser-readiness gaps. `rbush` and `flatbush` should wait until the snapping/constraint workload is defined.

## Decisions

The immediate recommended candidate is `polygon-clipping`, but only for a future isolated adapter spike that cross-checks polygon boolean/topology behavior in tests and review-only previews. The adapter should not repair or replace SolarPro canonical geometry, should not write to the database, should not mutate CAD, and should not feed permit/engineering/BOM decisions.

`martinez-polygon-clipping`, `@turf/turf`, `rbush`, `flatbush`, `dxf-writer`, `svg-pathdata`, `sharp`, and `tesseract.js` are reasonable later candidates under narrow adapters. `jsts` requires legal review before any production consideration. `opencv.js` should be rejected for now in the core app/parser path and reconsidered only as an optional worker after OCR/provenance infrastructure is stronger.
