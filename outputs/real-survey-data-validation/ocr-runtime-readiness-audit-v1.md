# OCR Runtime Readiness Audit V1

## Scope and sequencing

This audit was completed before any OCR runtime pilot implementation. The active branch is `dev`, and the baseline from Survey Ingestion Alignment + First Real Metadata Runtime Pilot V1 is present. The purpose of this document is to identify what OCR/text-extraction capability already exists, where it is coupled to bill or debug flows, how Survey V2 ingestion and assisted-evidence boundaries must be preserved, and what the smallest safe OCR runtime bridge may do after this audit.

The audit conclusion is that OCR capability already exists in the repository, but it is not currently governed as an assisted-evidence runtime. Existing OCR paths are mostly utility-bill and diagnostic paths. They extract and parse text, sometimes using external AI/vision services, and in several places convert text into structured bill facts. Those flows must not be imported wholesale into assisted evidence. The safe pilot path is a new governed assisted-evidence OCR runtime adapter/bridge that emits only `text_region_candidate` records through the existing candidate normalization and review-required flow, preserving OCR text as non-authoritative evidence and never converting text into engineering facts.

## Verified OCR and text-extraction dependencies

The repository already declares OCR/PDF/image-text-related dependencies in `package.json` and `package-lock.json`. The verified declarations include `tesseract.js` at `^7.0.0`, `pdf-parse` at `^2.4.5`, `@types/pdf-parse` at `^1.1.5`, `sharp` at `^0.34.5`, `canvas` at `^3.2.1`, `html2canvas` at `^1.4.1`, and `jspdf` at `^4.2.0`. The lockfile also contains `node_modules/tesseract.js`, `node_modules/tesseract.js-core`, `node_modules/pdf-parse`, `node_modules/pdfjs-dist`, `node_modules/canvas`, and `node_modules/@napi-rs/canvas` entries. Therefore, Tesseract/OCR support is already present through `tesseract.js`; the native `tesseract` CLI is referenced by code and checked dynamically with `tesseract --version`, but binary availability remains runtime-environment dependent.

No new OCR dependency is required for the first pilot. Adding OpenCV, TensorFlow, YOLO, ONNX, MediaPipe, segmentation, object detection, semantic visual classification, geometry extraction, or any new model runtime would violate the directive and is not needed for text-only OCR evidence.

## Existing OCR and text-extraction usage

The most direct OCR route is `app/api/ocr/route.ts`. It is a dedicated server-side OCR endpoint using Tesseract. The route declares `runtime = 'nodejs'`, requires authentication through `requireAuth(req)`, applies OCR rate limiting through `checkRateLimit('ocr', getClientIp(req))`, accepts base64 image input, optionally imports `preprocessBillImage` from `lib/billImagePreprocess.ts`, and executes a multi-pass Tesseract flow. The route prefers native Tesseract CLI when available, then falls back to `tesseract.js` WASM via `createWorker` and `worker.recognize`. It returns raw OCR text, confidence, method, and debug logs. Its own comments state that it is called internally by `bill-upload/route.ts`, not by the browser. This route proves OCR is installed and operationally isolated for bill OCR, but it is still an API route, not an assisted-evidence adapter. It logs raw OCR text, imports bill-specific preprocessing, has API/auth/rate-limit concerns, and should not be directly imported into assisted-evidence source code.

The main production-like OCR integration is `app/api/bill-upload/route.ts`. That route imports bill parsing and extraction helpers, including `parseBillText`, `validateBillData`, `extractBillDataWithAI`, `extractPdfTextPure`, and `extractBillWithClaude`. It supports PDF extraction through `pdftotext`, `pdf-parse`, a pure fallback, `pdfjs-dist`, OpenAI Files/Responses, and Google Vision. For images, it uses Claude direct image extraction first when available, then falls back to Tesseract CLI, local Tesseract WASM through the internal OCR route, OpenAI Vision, and Google Vision. It then parses text through `parseBill` and `parseBillText`. This is more than raw OCR: it converts bill images/PDFs into utility bill facts and can choose external AI/vision outputs based on parsed usage. It must not be reused as the assisted-evidence OCR runtime bridge.

The diagnostic routes `app/api/debug/ocr/route.ts` and `app/api/debug/bill/route.ts` also contain OCR and PDF extraction logic. The OCR debug route reads uploads, tries PDF text extraction or image OCR, and reports debug fields such as method, confidence, text length, and preview text. The bill debug route performs OCR and then bill parsing. These routes are useful as audit evidence that the codebase has OCR/text extraction, but they are diagnostic and not governed assisted-evidence runtimes.

The helper `lib/billOcrEngine.ts` defines an `OcrResult` with `rawText`, `confidence`, and method values including `tesseract-js`, `tesseract-cli`, `openai-vision`, `google-vision`, and `none`. Its `recognizeImage()` calls the internal `/api/ocr` route. It also exposes `recognizeImageWithVision()` and `recognizeImageWithGoogle()`, both direct external AI/vision integrations. This helper is coupled to bill OCR fallback behavior and should not be imported as-is for the first assisted-evidence OCR runtime. At most, the pilot can reuse the fact that `tesseract.js` is already installed and reuse safe text-normalization concepts while avoiding bill parser and external AI/vision escalation.

The helper `lib/billImagePreprocess.ts` uses `sharp` to rotate, resize, grayscale, normalize, and sharpen bill images before OCR. This may improve bill OCR but is bill-specific. The first assisted-evidence OCR pilot should avoid adding new image preprocessing unless absolutely necessary, because preprocessing could be mistaken for image-quality/metadata runtime logic and could overlap the recently governed metadata/runtime boundaries. If preprocessing is later added, it must remain OCR-only and must not create blur, quality, EXIF, duplicate, or engineering signals.

The modules `lib/billOcr.ts`, `lib/billParser.ts`, `lib/billPipeline.ts`, `lib/billClaudeExtractor.ts`, `lib/billConfidence.ts`, `lib/billEnrichment.ts`, and related bill/intake files parse or enrich bill information. These should not be reused for OCR assisted evidence, because the pilot is limited to text-only candidates and must not convert OCR text into canonical utility, account, address, usage, rate, service, or engineering facts.

## Upload and file text-extraction audit

Existing upload/file text extraction is concentrated in bill upload and debug flows. Utility bill upload accepts PDFs and images, extracts text using multiple mechanisms, and parses or validates structured bill data. PDF parsing uses `pdftotext`, `pdf-parse`, `pdfjs-dist`, and fallback pure extraction. Image text extraction uses Tesseract CLI/WASM and can escalate to OpenAI Vision, Google Vision, or Claude image extraction depending on path and environment.

Meter labels, equipment labels, placards, nameplates, and survey images are not currently connected to a governed OCR runtime. The assisted-evidence namespace contains a fixture-only OCR-like adapter, `lib/assistedEvidenceSources/ocrFixtureAdapter.ts`, which emits fixture text signals for `possible_meter_label_text` and `possible_equipment_label_text`. That adapter explicitly records `fixtureOnly: true`, `no-ocr-runtime`, `text-fixture-only`, and `review-required`. It is a style reference for candidate normalization, but it is not a runtime OCR implementation.

## Survey V2 ingestion links and lifecycle

Survey V2 ingestion already has canonical survey and attachment pathways. The relevant audited namespace includes `lib/survey/v2/types.ts`, `lib/survey/ingest/types.ts`, `lib/survey/ingest/transformLayer.ts`, `lib/survey/ingest/ingestPipeline.ts`, `lib/survey/evidence/manifest.ts`, `lib/db/surveys.ts`, and API routes under `app/api/survey`, `app/api/site-surveys`, and project site-survey routes. The completed Survey Ingestion Runtime Alignment phase established that `site_surveys` and `site_survey_files` remain the canonical field survey and attachment/photo sources. The metadata runtime bridge reuses existing upload identity, categories, hashes/provenance where provided by ingestion, and existing image metadata/quality values without duplicating storage, upload, hashing, blur, or metadata systems.

The OCR runtime pilot must follow the same pattern. It may consume an existing survey attachment identity and image bytes, but it must not create, update, upsert, or delete `site_surveys`, `site_survey_files`, `project_physical_data`, survey evidence manifests, survey ingestion payloads, or project physical projections. It must preserve source provenance and deterministic source context in candidate payloads. It must not introduce a new upload lifecycle, file store, attachment table, image hash, blur score, metadata parser, duplicate detector, or review workflow.

## Assisted-evidence integration audit

The assisted-evidence runtime framework already provides the correct safe path. `lib/assistedEvidence/candidateLifecycle.ts` creates candidates with `nonAuthoritative: true` and `reviewRequired: true`; `markReviewRequired()` moves candidates into the `review_required` status. `lib/assistedEvidenceSources/candidateNormalization.ts` routes normalized adapter outputs through `assertToolCanEmitCandidateType()`, `createCandidate()`, and `markReviewRequired()`, while adding registry hash, runtime category, allowed boundary, deterministic input refs, non-authoritative limitations, and review-required limitations.

The open-source registry in `lib/assistedEvidenceSources/openSourceToolRegistry.ts` currently has a fixture OCR entry, `fixture-ocr-text-adapter@1.0.0`, with runtime category `fixture_only`, allowed candidate type `text_region_candidate`, review required, canonical mutation forbidden, and fixture replay only. The runtime registry currently includes `sharp-metadata-runtime@0.34.5` but does not yet include a real OCR runtime. Therefore, any OCR runtime implementation must first add a governed runtime registry definition, likely for `tesseract.js@7.0.0`, with `runtimeCategory` describing OCR/text extraction, `allowedCandidateTypes: ['text_region_candidate']`, `reviewRequired: true`, `canonicalMutationAllowed: false`, server-only execution, native-binary dependency accurately declared, deterministic replay support via runtime payload hashes, and a boundary such as OCR text extraction only.

The adapter contract in `lib/assistedEvidenceSources/candidateAdapterContracts.ts` defines runtime adapters as server-only and adapter-contained and states that adapters must output normalized candidate payloads only, route candidate creation through `createCandidate()` and `markReviewRequired()`, avoid canonical evidence/engineering/CAD/recommendation/workflow imports, and avoid implicit confidence upgrades. A real OCR runtime should add an OCR runtime adapter type parallel to `MetadataCandidateRuntimeAdapter`.

Candidate category/type support already includes `text_region_candidate` in assisted-evidence types. Existing OCR fixture candidates demonstrate that text candidates can use categories such as `field_context` and `electrical_context`. The first runtime pilot should continue to emit `text_region_candidate` only; the candidate payload `field` values may be the directive-approved text-only labels, but candidate type should remain the governed text-region type.

## Boundary risk audit

The highest boundary risks are all caused by importing the wrong existing OCR code. The utility bill upload route and bill parser convert OCR text into structured utility/bill facts. The debug routes are not governed runtimes. `lib/billOcrEngine.ts` can call external OpenAI and Google Vision services and returns confidence values that are not deterministic Tesseract-only outputs. `lib/billImagePreprocess.ts` performs image transformations that could blur the boundary with metadata/quality logic if reused broadly. These risks mean the assisted-evidence OCR runtime should be implemented as a new narrow adapter/bridge inside `lib/assistedEvidenceSources/`, not as an import of bill upload, bill parser, debug route, or bill OCR engine.

The current assisted-evidence boundary guard already blocks prohibited runtime patterns under assisted-evidence source files, including `tesseract`, `createWorker(`, and `recognize(`, and also blocks direct canonical mutation, database mutation, survey table mutation, CAD readiness, recommendations, workflows, duplicate metadata/hash systems, blur logic, and unapproved image-byte analysis. This is correct for the pre-OCR state but must be expanded carefully for the OCR pilot. The expansion should approve Tesseract imports only in the dedicated OCR runtime adapter file and should continue to fail OCR imports or OCR-like runtime execution anywhere outside the governed OCR adapter/bridge/test allowlist. It should also fail if OCR code touches `site_surveys`, `site_survey_files`, `project_physical_data`, CAD readiness, recommendations, workflows, engineering requirement evaluation, bill parsers, canonical mutation APIs, database mutation APIs, or confidence-upgrade patterns.

## Is OCR output canonical or authoritative today?

No existing assisted-evidence OCR runtime output is canonical or authoritative. The existing `ocrFixtureAdapter` emits fixture-only review-required candidates. Separately, the bill upload OCR/parser flows can produce structured bill data for the bill/intake domain, but those are not governed assisted-evidence candidates and must not be treated as canonical survey/engineering evidence. For the OCR runtime pilot, all OCR output must be non-authoritative, review-required, text-only evidence. Even after human review, the assisted-evidence projection may be eligible for mapping only through the existing review projection flow; OCR runtime itself must never mutate canonical evidence or set engineering facts.

## Code that may be reused

The first pilot may reuse the installed `tesseract.js@7.0.0` dependency, the assisted-evidence candidate normalization pipeline, `createReviewRequiredCandidates()`, `getRegisteredOpenSourceTool()`, registry validation, confidence normalization helpers, deterministic hashing from `lib/assistedEvidence`, and the adapter style demonstrated by `ocrFixtureAdapter.ts` and `metadataRuntimeAdapter.ts`. It may reuse safe text normalization concepts such as trimming and whitespace normalization, but should keep them in the OCR runtime adapter/bridge so that bill-specific correction rules are not imported.

## Code that must not be duplicated or imported wholesale

The pilot must not duplicate or import survey ingestion, survey upload handling, file storage, attachment lifecycle, hashing/fingerprinting systems, metadata runtime extraction, blur/quality scoring, duplicate detection, bill parsing, bill intelligence enrichment, utility bill fact extraction, review workflow, CAD readiness, recommendations, workflow orchestration, engineering requirement satisfaction, or canonical database mutation. It must not import `app/api/bill-upload/route.ts`, `app/api/debug/ocr/route.ts`, `app/api/debug/bill/route.ts`, `lib/billOcr.ts`, `lib/billParser.ts`, `lib/billPipeline.ts`, `lib/billClaudeExtractor.ts`, or external vision helpers as the assisted-evidence OCR runtime.

## Safest bridge for implementation after this audit

The safest bridge is a new, narrow assisted-evidence source implementation under `lib/assistedEvidenceSources/`. The likely files are `ocrRuntimeTypes.ts`, `ocrRuntimeAdapter.ts`, and `ocrRuntimeBridge.ts`, following existing naming and style. The adapter should be registered as a governed runtime, extract raw text with `tesseract.js` only, normalize text deterministically, reject empty OCR results safely, preserve raw confidence without silent upgrades, build deterministic runtime payload hashes, and emit only `text_region_candidate` outputs through `createReviewRequiredCandidates()`.

The bridge should accept an explicit source reference from existing survey attachment context, similar to `surveyIngestionRuntimeBridge.ts`, and annotate candidates with source identity, canonical source-of-truth, `canonicalMutationAllowed: false`, `runtimePilot: true`, `runtimeLabel`, OCR method, runtime payload hash, and the exact text-only field label. It should not classify equipment authoritatively. It should not parse OCR text into panel ratings, breaker sizes, service account truth, addresses, placards, invoices, nameplates, or service facts.

## Safe first candidate payload field labels

The first pilot may use only these text-only candidate payload `field` labels: `possible_utility_account_number`, `possible_meter_number`, `possible_service_panel_rating_text`, `possible_breaker_rating_text`, `possible_equipment_label_text`, `possible_address_text`, `possible_placard_text`, `possible_invoice_or_bill_text`, `possible_nameplate_text`. The non-`*_text` labels in this allowed list, such as `possible_utility_account_number` and `possible_meter_number`, must still be represented as possible OCR text, not confirmed account or meter facts. The runtime must not confirm a panel rating, set breaker size, satisfy a requirement, or mutate canonical fields from OCR text.

## Boundary checks required before or during implementation

Before the OCR runtime pilot is considered complete, `scripts/check-assisted-evidence-boundaries.js` must be expanded to enforce the following: Tesseract imports and OCR execution are allowed only in the governed OCR runtime adapter and relevant tests; OCR bridge files may delegate only to the approved OCR runtime adapter; OCR output must route through registered tool lookup and candidate normalization; candidate creation must remain `createCandidate()` plus `markReviewRequired()` through `createReviewRequiredCandidates()`; OCR files must not import bill upload, bill parser, bill pipeline, bill Claude extractor, OpenAI Vision, Google Vision, survey ingestion, survey evidence, DB survey modules, CAD readiness, recommendations, workflows, engineering requirement evaluation, or project physical data modules; OCR files must not contain database mutation or canonical mutation patterns; OCR candidate payloads must include `canonicalMutationAllowed: false`; OCR confidence must be preserved or normalized downward only and must not be silently upgraded; OCR code must not contain engineering-fact conversion patterns such as setting panel rating, breaker size, service size, roof geometry, CAD state, requirement satisfaction, recommendation state, workflow items, or project physical fields.

## Readiness decision

The repository is ready for a very small OCR runtime pilot only if implementation stays inside the assisted-evidence source boundary and uses the existing candidate/review registry flow. Tesseract/OCR is already present through `tesseract.js`; native Tesseract CLI is optional and environment-dependent. Existing bill OCR and debug code proves OCR capability but is too broad and too coupled to bill parsing and external vision services for direct reuse. The approved first implementation should be Tesseract text extraction only, deterministic, review-required, non-authoritative, and prohibited from canonical or engineering mutation.
