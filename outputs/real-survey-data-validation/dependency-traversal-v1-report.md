# Dependency Traversal V1 Report

## Pre-implementation audit

This report documents the current dependency graph and traversal semantics before implementing deterministic Dependency Traversal V1.

The primary existing dependency graph type is `EngineeringDependencyGraph` from `lib/documentProvenance/types.ts`. It contains nodes with types such as engineering requirement, canonical evidence, permit section, SLD section, BOM row, CAD layout primitive, render context, engineering assumption, engineering decision, calculation, and render output. Edge types include `satisfies_requirement`, `binds_requirement_to_document`, `feeds_render_context`, `supports_geometry_assumption`, `supports_electrical_assumption`, `supports_structural_assumption`, `documents_missing_requirement`, `explains_engineering_decision`, `decision_uses_requirement`, `decision_uses_evidence`, `decision_feeds_document`, `decision_feeds_bom`, `decision_feeds_sld`, and `decision_feeds_render_output`.

Current graph generation is performed in `lib/documentProvenance/builders.ts`. Requirement evaluation produces requirement nodes. Canonical evidence records produce evidence nodes. Evidence-to-requirement edges use `satisfies_requirement`. Requirement-to-document-section edges use `binds_requirement_to_document` or `documents_missing_requirement`. Geometry wrapper metadata creates assumption/input-like nodes and support edges, but the code treats them as deterministic metadata and not inferred geometry. A primary render context node is added. Current render context section relationships include render-context-to-section edges with `feeds_render_context`, while decision provenance adds requirement-to-decision, evidence-to-decision, decision-to-document-section, and decision-to-render-context relationships. This means V1 must not assume that every requested conceptual dependency direction already exists in the physical edge direction used by the current graph.

Persistent graph generation occurs in `lib/engineeringStateInvalidation/persistence.ts`. `buildPersistentEngineeringStateGraph()` creates state graph nodes for engineering state records and dependency graph nodes for every referenced dependency id. It adds `depends_on_dependency_node` edges from dependency graph nodes to state graph nodes. Invalidation results add `invalidates_state` edges from triggering dependency nodes to invalidated state nodes, or a deterministic self-loop fallback when no triggering dependency exists. Additional edge types include `preserves_stale_state` and `supersedes_snapshot`. This persistent graph is suitable for lineage display but not yet a complete traversal API.

Existing traversal is embedded in `reachableDependencyIds()` in `lib/engineeringStateInvalidation/engine.ts`. It seeds changed dependency node ids, changed canonical evidence ids mapped to `canonicalEvidence:{id}`, changed requirement ids mapped to `requirement:{id}`, and changed decision ids as-is. It follows `EngineeringDependencyGraph.edges` from `fromNodeId` to `toNodeId`, using a set to avoid revisiting nodes. The traversal returns only a set of reachable ids. It does not return paths, edge classifications, depth, duplicate-edge observations, missing-node observations, cycle indicators, or truncated traversal metadata.

The current traversal model is deterministic because input arrays are normalized elsewhere and visited-set traversal prevents repeated expansion. However, deterministic output is limited to reachable membership. The V1 graph engine must reconstruct one or more stable dependency chains for each impacted node, support upstream and downstream tracing, classify edges, group impacted nodes by type/output class, expose traversal depth, and record cycle protection behavior. It must also retain deterministic ordering by sorting node ids, edge ids, and path ids lexicographically before output.

Cycle and infinite-loop risks are currently mitigated but not reported. A cycle in the document provenance graph should not cause infinite traversal because a node already in the visited set will not be enqueued again. However, there is no maximum traversal depth, no maximum edge visit count, and no explicit cycle report. A pathological graph with a very large number of unique nodes could still create expensive traversal. V1 must implement explicit traversal limits, stable truncation metadata, and cycle detection indicators without hiding affected stale state.

Duplicate edge handling is currently implicit. Document provenance builders often use helper insertion to avoid duplicate edges, and state invalidation hashing sorts/de-duplicates many values. Traversal V1 must still handle duplicate edges defensively because persistent graph edges, merged graph sources, and future imported graph metadata may contain duplicates. Duplicate edges should not alter affected-node membership or deterministic hashes, but should be represented as normalized or duplicate-suppressed metadata when relevant.

Missing-node behavior is currently tolerant because traversal follows edge endpoints and matching records by ids; absent graph nodes generally do not crash traversal. V1 must make this explicit by reporting missing source nodes, missing target nodes, missing state records, missing snapshot refs, and missing evidence ids as `NOT_LOADED`, `BLOCKED`, or `REQUIRES_REVIEW` depending deterministic cause. It must never fabricate node metadata to fill gaps.

Lineage semantics today are split across document provenance dependency graphs, decision provenance dependency ids, engineering state record fields, persistent graph nodes/edges, transition history, timeline, stale metadata, invalidation lineage metadata, and workspace summaries. V1 must combine these into a traversal result without rewriting truth. The result should preserve source ids and reasons, identify whether a path came from document provenance graph, persistent state graph, state record references, transition history, or snapshot refs, and keep the source type auditable.

## Required V1 traversal semantics

Dependency Traversal V1 must support deterministic downstream tracing for evidence to requirement, requirement to decision, decision to output, decision to document section, decision to render context, document section to render context where supported by existing metadata or reverse lookup policy, and snapshot to stale propagation. It must also support upstream tracing for output back to decision, requirement, evidence, snapshot, and graph node lineage.

The traversal engine must not create semantic relationships that are not present in existing metadata. If a requested conceptual relationship is not represented by an edge in the current graph, V1 should either use an explicitly documented reverse traversal mode over an existing edge or report the relationship as missing/not loaded. It must not infer scene content, image content, geometry, CAD layout, or engineering conclusions.

Each traversal result should include a stable traversal id, source node id, target node id, direction, edge ids, edge types, node ids in path order, depth, cycle detected flag, truncated flag, missing-node ids, duplicate-edge ids suppressed, deterministic reason, and source graph identifier where available.

## Implementation and Validation Result

Dependency Traversal V1 was implemented in `lib/engineeringIntelligence/propagationGraph.ts`. Traversal now merges document dependency graph and persistent engineering state graph metadata into a deterministic propagation graph with stable sorting, duplicate-edge suppression, missing-node reporting, path reconstruction, upstream/downstream traversal, max-depth and traversal-limit controls, and explicit cycle/truncation indicators. The traversal does not inspect document images, infer geometry, classify scenes, or synthesize engineering conclusions.

Focused regression coverage and the full suite validated cycle handling, duplicate edge suppression, missing target reporting, deterministic reruns, and traversal-safe workspace consumption. Final validation passed with prohibited-boundary scan, topology check, type-check, full tests, build, and lint all returning exit code `0`.
