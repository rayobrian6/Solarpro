# Geometry-Adjacent Assistance Governance Readiness Audit V1

## Scope and Safety Position

This audit was performed as a governance and architecture phase only. No geometry extraction, roof detection, roof plane generation, object detection, segmentation, CAD mutation, topology mutation, NEC mutation, layout-engine mutation, or engineering-authority mutation was implemented. The current platform already contains deterministic geometry, CAD, layout, route, rendering, and engineering-coupling systems. This report identifies where that existing deterministic authority lives so that future probabilistic or assisted geometry-adjacent systems can be contained before any such runtime exists.

The critical invariant for this phase is that probabilistic runtime systems remain isolated from deterministic engineering authority. The audit confirms that future geometry-adjacent assistance must not enter the existing CAD, roof, layout, conductor routing, production, structural, BOM, or plan-set authority paths directly. Any future geometry assistance must remain review-required, non-authoritative, provenance-preserved, replayable candidate evidence until a human review process explicitly maps an accepted projection into a separately governed deterministic truth path.

## Current Deterministic Roof and Layout Architecture

The current roof and layout stack is deterministic and already geometry-authoritative in several places. `lib/roofGeometry.ts` provides local coordinate conversion, polygon area and centroid math, polygon shrinking, edge alignment support, and panel-grid CAD generation utilities. Its functions include `latLngToLocal`, `localToLatLng`, `polygonCentroid`, `computeRoofCentroid`, `polygonAreaM2`, `shrinkPolygonFeet`, `shrinkPolygon`, and geometry helpers that support panel placement and setback calculations. `lib/roofPlane3D.ts` provides 3D vector math and plane framing helpers, including `projectOntoPlane`, `mostHorizontalEdgeAxis`, and 3D frame construction. `lib/planeEngine.ts` defines plane frames, panel dimensions, grid spacing, setbacks, UV points, ENU/ECEF conversion, plane construction from two points, and plane construction from azimuth/tilt.

`lib/panelLayout.ts` contains simpler roof, ground, and fence layout generation functions. Its `generateRoofLayout` computes roof-plane bounding boxes from vertices, applies uniform setbacks in latitude/longitude approximations, converts panel dimensions and row/column spacing into degree offsets, and places panels on a grid. Its `generateGroundLayout` and `generateFenceLayout` similarly place panels using deterministic geometric calculations. This module is geometry-authoritative because it creates panel positions, panel orientation, row/column placement, and system layout outputs from deterministic inputs.

`lib/panelLayoutOptimized.ts` is a more advanced CAD geometry engine for roof panel layout. Its header describes `portrait`, `landscape`, and `hybrid` orientation behavior. The audit found that `generateRoofLayoutOptimized` delegates to a portrait-first three-pass solver when orientation is `hybrid` or undefined. `solveRoofLayout` runs portrait-only, landscape-only, and mixed-fill passes; scores them; and chooses a winning layout with tie ordering of portrait over mixed over landscape. `runPass` delegates to `generatePanelGridCAD`, which is treated in comments as the authoritative row-iteration loop. `buildMixedFill` uses portrait rows plus a landscape strip in the remaining roof area. This is deterministic but geometry-authoritative because it makes panel placement, row, orientation, and fit decisions based on roof polygon, setbacks, azimuth, and panel dimensions.

`lib/placementEngine.ts` provides grid snapping, fire setback zones, azimuth-aligned grid rotation, multi-row generation, auto-fill with setbacks, ground array generation, fence array generation, row spacing calculation, and regeneration with orientation. It defines `FireSetbackConfig`, `GridSnapConfig`, `SetbackZone`, `MultiRowParams`, and `AutoFillParams`. Functions such as `snapToGrid`, `buildGridConfig`, `calcEffectiveSetback`, `getPerEdgeSetbacks`, `generateSetbackZones`, `insetPolygon`, `generateAlignedGrid`, `generateMultipleRows`, `autoFillWithSetbacks`, `generateGroundArray`, `generateFenceArray`, `calcMinRowSpacing`, and `regenerateWithOrientation` are geometry-affecting surfaces. The module comments explicitly distinguish uniform visual-overlay setbacks from per-edge CAD solver setbacks. Future geometry candidates must not call these functions to create canonical layouts or modify their inputs automatically.

`lib/engineering/fire-setbacks.ts` calculates code-related setback requirements. Its `calcFireSetbacks` accepts inputs such as roof type, roof pitch, roof area, state, fire zone, and AHJ overrides, then returns required eave, ridge, hip, valley, side, and pathway setback values, usable roof area estimates, notes, special requirements, and code references. This module is deterministic engineering authority because it encodes IRC, WUI, CAL FIRE, and AHJ-related rules. Future geometry assistance must not convert candidate roof-edge, ridge, valley, or obstruction hints into setback compliance results automatically.

## Current CAD and Rendering Architecture

The current CAD stack has an explicit solved-model architecture. `lib/cad/cadEngine.ts` is the root entry point. Its comments state that `generateCADLayout(input)` resolves a CAD system type, calls a system-specific solver (`roofCAD`, `groundCAD`, or `fenceCAD`), returns a `CADModel`, then adapts the result to drafting. The comments also state that the CAD model is the single source of truth and that the drafting engine is rendering only. This is a key deterministic authority boundary. Any future geometry-adjacent assistance must not be permitted to write into `CADModel`, invoke `generateCADLayout`, or bypass the CAD solver by producing drafting-ready geometry.

`lib/cad/types.ts` defines `CADPanel`, `CADRoofPlane`, `CADGroundArray`, `CADFenceSegment`, `CADDimension`, `CADObstruction`, `CADElectricalNode`, `CADConduitRoute`, and the top-level `CADModel`. The audit found important risk language in the current types: `CADObstruction` is described as vision-sourced and used by `roofCAD.ts` to render exclusion zones and avoid panels within an obstruction radius plus setback; `CADElectricalNode` is described as a detected electrical component; `CADConduitRoute` includes route methods including `vision_guided`, `shortest_path`, and `fallback_straight`. These are existing geometry-adjacent risk surfaces even if no new geometry intelligence is implemented in this phase. Future runtime candidates must not populate these CAD types directly.

`lib/cad/roof/roofCAD.ts` is the deterministic roof CAD solver. Its comments state that it applies true polygon setbacks per plane and keeps geometry logic out of rendering templates. The audit found deterministic calculation of panel dimensions, default eave/ridge/rake setbacks, roof-plane polygon conversion from lat/lng into local XY, `insetPolygon` usage, bounding boxes, polygon area, GPS panel handling, grid generation, panel rows and columns, obstruction filtering, and CAD roof-plane outputs. It filters panels by obstructions using a combined radius and setback zone. This file is a critical geometry authority surface because it converts project geometry into solved CAD roof planes, usable polygons, panels, dimensions, setbacks, obstructions, and panel counts.

`lib/cad/adapter.ts` converts a solved `CADModel` into drafting input. Its comments state that it overwrites only geometry fields with CAD-solved values and preserves non-geometry engineering, compliance, and other data. It converts CAD roof planes and panels into project roof planes and panel positions, and uses a fake-degree encoding for local XY coordinates. This is an output mutation path from CAD geometry into drafting/rendering. Future geometry candidates must not enter this adapter or generate fake-degree drafting fields directly.

`lib/cad/buildCADFromSurvey.ts` is a survey-to-CAD bridge. Its comments state that it does not solve the layout; instead, it constructs CAD inputs from an enriched site survey. It converts CAD-ready surfaces into partial CAD roof-plane inputs, sets usable polygons from enriched setback-inset polygons, constructs ground-array inputs, and builds overrides such as roof pitch, azimuth, tilt, rafter spacing, and structural/material fields. This bridge is a deterministic coupling point between canonical survey evidence and CAD. Future geometry assistance must not be allowed to modify enriched survey geometry or CAD-ready surfaces automatically.

`lib/cad/mergeCADModels.ts` overlays survey-derived constraints onto a solved CAD model. The comments state that it never re-runs the CAD solver, never throws, returns the base CAD unchanged when survey inputs are absent or mismatched, and overlays fields such as system-definition layout azimuth and tilt. Even though it is defensive and deterministic, it is still a geometry mutation/coupling point. Future geometry candidates must not be used as survey-derived constraints for this merge step without a separate reviewed canonicalization process.

`lib/drafting/renderPlanSet.ts` defines the global render contract. Its comments state that no sheet may render without both a solved CAD model and a render context, and that `renderPlanSet` is the only public function generating plan-set sheets. It calls `buildRenderContext`, validates the system type, and dispatches to roof, ground, or fence sheet rendering. `lib/drafting/sheetComposition.ts` states that all values are CAD-driven and validates sheet composition before rendering. `lib/plan-set/site-layout-sheet.ts` renders roof outlines, panel placement diagrams, fire setbacks, ridge/eave/pathway dimensions, north arrow, and array dimensions. `lib/plan-set/structural-sheet.ts` computes structural load combinations and auto-fix spacing behavior based on structural input fields. `lib/sld-professional-renderer.ts` is a vector rendering surface for SLD equipment, conductors, annotations, and schedules. These rendering systems must remain downstream consumers of deterministic truth, not consumers of probabilistic geometry candidates.

## Current Spatial Dependency and Geospatial Architecture

`package.json` and `package-lock.json` show spatial and rendering dependencies including `cesium`, `three`, `mapbox-gl`, `@mapbox/mapbox-gl-geocoder`, `geotiff`, `sharp`, `canvas`, `html2canvas`, `jspdf`, `pdf-parse`, and related transitive geospatial packages. `components/3d/SolarEngine3D.tsx` describes a production 3D design engine using CesiumJS, Google Photorealistic 3D Tiles, GPU-instanced panel rendering, real-time shade engine behavior, and NaN/error guards around Cesium operations. The audit also found `components/3d/CesiumViewer.tsx`, `lib/topography/getTopographyState.ts`, `app/admin/topography/page.tsx`, `app/api/solar/route.ts`, `lib/shadeAnalysis.ts`, and proposal/design surfaces as spatially relevant files.

The presence of Cesium, Mapbox, Three.js, Google Solar API references, geotiff, shading, topography, 3D tiles, lat/lng conversion, local XY projection, ECEF/ENU conversion, and terrain/topography modules means future geometry assistance must be carefully separated from geospatial display and deterministic layout authority. A future runtime may not use these spatial libraries as a path to generate roof planes, detect obstructions, infer setbacks, derive routing, or mutate CAD. Display-only spatial components must not become geometry candidate runtimes without registry review, provenance, replay, and review lifecycle controls.

## Deterministic Engineering Coupling Points

Geometry currently affects deterministic engineering outputs through several paths. The first path is roof geometry into panel placement and system size. `panelLayout`, `panelLayoutOptimized`, `placementEngine`, and `roofCAD` determine panel count, orientation, rows, columns, placement coordinates, and total DC size. These values influence production estimates, plan-set diagrams, BOM quantities, and potentially structural and electrical calculations.

The second path is roof geometry into fire setbacks and usable area. `lib/engineering/fire-setbacks.ts`, `placementEngine` setback helpers, `roofCAD` polygon insets, and `site-layout-sheet` fire setback diagrams all encode setback geometry. Future candidates such as `possible_roof_edge_candidate`, `possible_ridge_candidate`, `possible_valley_candidate`, and `possible_obstruction_candidate` must never become setback compliance authority without review and deterministic re-evaluation.

The third path is geometry into CAD readiness and survey-to-CAD inputs. `buildCADFromSurvey` consumes enriched survey geometry and derived CAD-ready surfaces, while `mergeCADModels` overlays origin, azimuth, and tilt constraints. `lib/engineeringIntelligence/cadReadiness.ts` and the Engineering Intelligence UI display CAD readiness metadata. Future candidates must not mark CAD readiness as satisfied or directly unblock CAD generation.

The fourth path is geometry into routing and conductor assumptions. `lib/system/conduitRouting.ts` computes conduit routes for solved CAD models, uses CAD obstructions and electrical nodes, and writes `CADConduitRoute` outputs. `lib/bom/deriveRunLengths.ts` is a likely downstream surface for route length derivation and BOM effects. Future `possible_conduit_route_candidate` outputs must never become routing authority, conductor sizing authority, route length authority, or BOM mutation authority without a human-reviewed deterministic transition.

The fifth path is geometry into structural assumptions. `lib/plan-set/structural-sheet.ts`, `lib/structural-calc.ts`, structural engines, mounting hardware data, rafter spacing, roof pitch, roof material, attachment spacing, and load calculations are geometry-adjacent. Future `possible_attachment_region_candidate` outputs must never become attachment spacing, rafter mapping, structural adequacy, or load path authority.

The sixth path is geometry into rendering and plan-set outputs. `CADModel` feeds the drafting adapter, render plan set, sheet composition, site layout, structural sheets, and SLD/vector rendering. Future candidates must not modify plan-set outputs or drafting inputs directly.

## Existing Risk Map

The first risk is hidden geometry assumptions. Several modules use defaults for setbacks, roof system type, origin, roof dimensions, panel dimensions, row spacing, and fallback behavior. For example, `cadEngine` resolves system type from layout, project system type, or inferred layout data. `roofCAD` has default panel and setback values. `buildCADFromSurvey` falls back to roof system type and origin defaults when survey fields are absent. These deterministic defaults may be appropriate for current behavior but must not be silently satisfied by probabilistic candidates.

The second risk is silent spatial defaults. Latitude/longitude to local XY conversion, fake-degree encoding in the CAD adapter, and origin fallback behavior are deterministic but require clear provenance. Future candidates must include input coordinate systems, transform methods, projection origins, and replay hashes; otherwise stale propagation and review cannot be trusted.

The third risk is nondeterministic layout behavior through ordering, fallback, and mixed-strategy selection. The layout algorithms are deterministic for fixed inputs, but future candidates could change inputs such as roof polygon, setbacks, azimuth, tilt, obstruction position, route target, or panel orientation. That would change panel counts and outputs. Candidate review must expose exactly which deterministic inputs would change and must never apply those changes automatically.

The fourth risk is geometry state mutation. Existing bridges and merge modules can propagate survey-derived geometry into CAD outputs. Future geometry candidates must not be accepted into canonical survey geometry, enriched CAD-ready surfaces, `CADModel`, `DraftingInput`, or `SystemDefinition` unless a separate deterministic canonicalization workflow is designed and audited.

The fifth risk is CAD mutation through rendering-adjacent paths. Because `adaptCADToDrafting` overwrites geometry fields and `renderPlanSet` consumes solved CAD models, any future candidate that reaches those paths could alter plan-set outputs. Boundary guards must explicitly block geometry candidates from rendering and CAD adapter calls.

The sixth risk is route inference authority. `conduitRouting` currently calculates routes from CAD model data and can emit `vision_guided` as a route method in the CAD type model. Future route candidates must remain review-required hints only and must not generate conductor route lengths, bend counts, voltage drop assumptions, trench/conduit paths, or BOM data.

The seventh risk is geometry-derived engineering authority. Geometry can influence NEC calculations, conductor sizing, structural assumptions, production estimates, CAD readiness, routing assumptions, BOM generation, and plan-set outputs. Future geometry assistance must be explicitly forbidden from these outputs unless a human-reviewed deterministic truth transition has occurred and all downstream invalidation has been propagated.

## Readiness Conclusion

The platform has enough deterministic provenance, assisted-evidence lifecycle, runtime registry, boundary enforcement, dependency graph, snapshot, invalidation, and Engineering Intelligence workspace infrastructure to design future geometry-adjacent containment. However, it is not safe to implement geometry intelligence until explicit geometry candidate types, review lifecycle controls, provenance schema, invalidation mapping, and boundary guards are implemented and validated. The existing deterministic geometry stack is powerful and already authoritative; therefore future geometry assistance must start as non-authoritative, review-required candidates only and must be prevented from reaching CAD, engineering, routing, topology, production, BOM, or plan-set mutation paths.
