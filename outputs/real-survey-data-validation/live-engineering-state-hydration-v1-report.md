# Live Engineering State Hydration v1 Report

## Scope

This report documents the live Engineering Intelligence Workspace hydration added for project-scoped survey records. The implementation moves the project workspace beyond registry-only empty states when real project survey records and site survey files are available, while preserving explicit non-fabricated empty states when no survey source exists or database loading fails.

## Implemented data flow

The project hydration adapter follows the required deterministic architecture direction: survey ingestion/history feeds canonical evidence, requirement evaluation, provenance/traceability, dependency graph construction, engineering state registry creation, stale-state invalidation planning, snapshot and timeline hydration, selective regeneration planning metadata, and finally the Engineering Intelligence route/UI context.

The implementation is centered in `lib/engineeringIntelligence/projectHydration.ts`. Database-backed route loading uses `hydrateProjectEngineeringIntelligenceFromDb({ projectId, userId })`, which loads project surveys and survey files through the existing site-survey DB accessors. Testable deterministic hydration uses `hydrateProjectEngineeringIntelligence({ projectId, sources })`, which accepts explicit survey/file sources without requiring database access.

Raw project survey records are converted into the existing canonical site survey pipeline by building a conservative `RawSurveyPayload`, passing it through `normalizeSurvey()`, and then through `enrichSurvey()`. This prevents manual fabrication of incomplete `EnrichedSiteSurvey` objects and ensures existing normalization/enrichment rules produce derived field evidence. Survey files are classified into survey photo references through deterministic label/filename mapping only.

## Hydrated workspace state

When survey sources exist, hydration now produces canonical survey evidence, requirement evaluation, document and decision provenance when available from the evidence layer, an engineering state registry, persistent graph models, baseline/latest engineering snapshots, snapshot diffs, transition history, timeline metadata, invalidation result metadata, selective regeneration plan metadata, audit guard results, and a hydrated `EngineeringIntelligenceWorkspaceModel` generated from project snapshots.

The project route `app/admin/engineering-intelligence/project/[id]/page.tsx` now obtains the current admin session user ID from the `solarpro_session` cookie, calls the DB-backed hydration adapter, and renders the hydrated workspace. If no valid session user exists, the route renders an explicit `not_loaded` hydration state and does not synthesize evidence, geometry, stale state, snapshots, or regeneration plans.

## UI surfaces

The shared Engineering Intelligence components now include `ProjectHydrationSummary`, which surfaces hydration source, survey count, snapshot count, regeneration plan count, canonical survey ID, invalidation event ID, state graph ID, canonical evidence count, requirement completion, and deterministic notes. Existing graph, stale invalidation, snapshot, and regeneration panels now receive hydrated model state through the project route when survey evidence is available.

## Deterministic boundaries

The invalidation event generated by hydration is a planning visualization derived from the selected canonical evidence ID. It does not trigger autonomous regeneration. Selective regeneration plans are metadata-only rows used by the workspace to show candidates, order, blockers, and preserved outputs. No generated CAD, permit documents, drawings, or regenerated artifacts are emitted by this feature.

## Regression coverage

`lib/engineeringIntelligence/projectHydration.test.ts` validates that explicit survey/file fixtures hydrate a project workspace with canonical evidence, requirement evaluation, persistent graph, baseline/latest snapshots, snapshot diffs, invalidation metadata, regeneration planning metadata, and CAD readiness metadata. The same test file verifies that empty input remains an explicit `not_loaded` state and does not synthesize evidence, geometry, stale state, graph, snapshots, invalidation, or regeneration plans.
