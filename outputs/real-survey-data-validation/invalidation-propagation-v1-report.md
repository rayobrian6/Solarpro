# Engineering State Invalidation + Dependency Propagation V1 Report

## Pre-implementation audit

This report documents the audit performed before implementing deterministic Engineering State Invalidation + Dependency Propagation V1. The audit was performed against the existing Engineering Intelligence and Engineering State Invalidation source files in the current `dev` checkout. No implementation code was written before this audit pass.

The current invalidation stack is split between `lib/engineeringStateInvalidation` and `lib/engineeringIntelligence`. The lower-level `lib/engineeringStateInvalidation/engine.ts` package builds engineering state records, accepts an explicit invalidation trigger, computes directly affected and propagated stale records, and emits deterministic invalidation results and selective regeneration plans. The higher-level `lib/engineeringIntelligence/projectHydration.ts` package hydrates a project by building survey evidence, document provenance, decision provenance, state registry, baseline/latest persistent graphs and snapshots, a simulated/latest evidence invalidation result, a snapshot diff, transition history, a timeline, audit guards, CAD readiness, photo grouping, and the UI workspace model.

The current stale-state model is intentionally metadata-oriented but too narrow for the requested V1 state taxonomy. `EngineeringStaleStatus` currently supports only `current`, `stale`, `blocked`, and `unknown`. Workspace status values include `satisfied`, `partial`, `blocked`, `missing`, `inactive`, `current`, `stale`, `invalidated`, `preserved`, `unknown`, and `not_loaded`, but these are display statuses rather than a deterministic invalidation engine taxonomy. V1 must introduce explicit stale classes `VALID`, `PARTIAL`, `STALE`, `INVALIDATED`, `BLOCKED`, `NOT_LOADED`, and `REQUIRES_REVIEW`, and must not silently map or upgrade/downgrade existing states without traceable reasons.

Current invalidation behavior is driven by `invalidateEngineeringState(input)`. A trigger contains changed canonical evidence ids, requirement ids, decision ids, dependency node ids, and hashes. The implementation computes a reachability set from graph edges and then marks a record stale when direct trigger ids match the record's canonical evidence, requirements, decisions, or dependency node ids, or when propagated dependency ids are reachable from the trigger. It emits `EngineeringInvalidationEvent` records, updated state records, affected/unaffected ids, deterministic notes, and audit guards. This is deterministic and avoids fabricating engineering state, but it does not expose full propagation paths, traversal depth, cycle indicators, edge classifications, affected render contexts, affected snapshots, or impacted output groups as first-class data.

The current propagation behavior is shallow. `reachableDependencyIds()` seeds changed dependency nodes plus canonical evidence, requirement, and decision identifiers. It builds adjacency from `EngineeringDependencyGraph.edges` using `fromNodeId -> toNodeId` and performs queue-based traversal. It uses a `reachable` set, so normal cycles will not cause infinite traversal. However, the traversal has no configurable limit, no maximum depth guard, no explicit cycle discovery metadata, no duplicate-edge reporting, no path reconstruction, and no downstream grouping by output class. V1 must preserve the deterministic set behavior while adding traversal reports that explain why every downstream item is affected.

The current trigger matching has an important boundary: records with state types `decision_provenance`, `engineering_calculation`, and `requirement_evaluation` are matched only by direct triggers. Other state records may be affected by propagated dependency ids. This prevents some propagation overreach, but it is implicit and not represented as an auditable edge policy. V1 must make traversal eligibility and edge classification explicit so deterministic behavior is explainable.

Current invalidation metadata exists in `EngineeringStateRecord`, `EngineeringInvalidationResult`, `EngineeringStaleStateMetadata`, and `EngineeringInvalidationLineageMetadata`. State records carry `dependencyNodeIds`, `requirementIds`, `decisionIds`, `canonicalEvidenceIds`, generation/provenance/dependency hashes, stale status, invalidation reason, truth source, and deterministic notes. This is sufficient evidence for deterministic invalidation but not yet sufficient for the requested affected-output planning model because affected document sections, render contexts, snapshots, document output sections, BOM rows, SLD sections, and dependency propagation chains are scattered across state records, plan fields, transition history, and workspace summaries.

Current regeneration behavior is metadata-only and does not execute regeneration. `buildSelectiveRegenerationPlan(input)` reads stale records and groups affected document sections, engineering decisions, render contexts, BOM rows, SLD sections, layout primitives, blocked dependencies, regeneration order, unchanged preserved outputs, stale state ids, deterministic hash, deterministic notes, and optional snapshot reference. This satisfies the truth boundary that planning must not regenerate outputs. The gap is that the plan does not yet carry a structured upstream trigger chain, propagation paths, missing evidence, edge classifications, snapshot deltas, or explicit review requirements.

Current stale impact visualization is generated in `lib/engineeringIntelligence/workspace.ts` and rendered by `StaleInvalidationWorkspace`. It derives stale outputs from the latest snapshot, invalidation chains from transition history, preserved outputs and regeneration candidates from plans, and deterministic notes that explicitly state regeneration is visualization only. This UI is safe-rendered after the prior render-safety fix, but V1 needs richer visualization workspaces for propagation chains, invalidation sources, affected outputs, affected document sections, affected render contexts, affected snapshots, dependency traversal paths, upstream/downstream lineage, propagation depth, and cycle protection indicators.

Current truth boundaries are explicit in CAD readiness and photo grouping notes and partially enforced by invalidation guards. The code documents that CAD readiness is deterministic metadata only, uses canonical evidence categories and explicit survey physical fields only, and does not use image bytes, OCR, OpenCV, YOLO, semantic inference, or hallucinated geometry. Photo grouping likewise states grouping is based on metadata such as timestamps, filename order, submitted category, canonical category, dimensions/orientation metadata, and stable ids; probable side/continuity labels are metadata grouping context, not engineering truth or geometry. V1 must preserve these boundaries and add repository-level prohibited-boundary scans that distinguish prohibited runtime use from documented future capability flags.

Unsafe assumptions and risks identified before implementation are as follows. First, project hydration currently models a latest canonical evidence id as a selective invalidation trigger for visualization, which is useful for demos but should not be represented as autonomous evidence change detection. Second, the existing reachability traversal avoids infinite loops by visited set but does not expose cycles or enforce a traversal/depth limit. Third, current graph direction is inherited directly from document provenance edges, but requested V1 flows such as document section to render context may not always match existing edge direction because the current document provenance builder includes render-context-to-section edges and decision-to-render-context edges. Fourth, fallback/default decision behavior is documented in decision provenance but not a first-class invalidation trigger class. Fifth, CAD readiness transitions and grouped CAD readiness are not yet connected to stale propagation. Sixth, snapshot diffs compare state refs and hash vectors but do not explain invalidation causes or regenerated candidates. Seventh, workspace models are safe-rendered but V1 must ensure new Map, Set, bigint, Date, sparse array, null transition, and partial metadata surfaces never render raw objects.

## Implementation requirements derived from audit

The V1 invalidation engine must operate only on canonical evidence ids, requirement ids, decision ids, dependency node ids, existing graph metadata, persistent state records, snapshots, and explicit CAD/readiness metadata. It must not inspect image bytes, perform OCR, run CV/ML models, infer geometry, generate CAD, or make engineering decisions. It must return deterministic metadata describing stale propagation and planning only.

The V1 propagation output must include upstream trigger, affected state ids, affected output ids, invalidated decisions, affected document sections, affected render contexts, affected snapshots, propagation paths, traversal depth, cycle indicators, blocked/missing evidence, stale class, and deterministic notes. It must be safe for sparse surveys, missing graph nodes, duplicate edges, invalid snapshots, null transitions, snapshot divergence, and deterministic reruns.

## Implementation and Validation Result

Invalidation Propagation V1 was implemented as deterministic metadata-only propagation in `lib/engineeringIntelligence/invalidationEngine.ts`, backed by scoped traversal from `lib/engineeringIntelligence/propagationGraph.ts`. The implementation maps existing engineering state records into the requested stale classes `VALID`, `PARTIAL`, `STALE`, `INVALIDATED`, `BLOCKED`, `NOT_LOADED`, and `REQUIRES_REVIEW` without inventing state. Affected outputs, affected document sections, render contexts, invalidated decision metadata, missing evidence identifiers, snapshot impact identifiers, CAD readiness transition identifiers, cycle-protection metadata, and deterministic hashes are derived only from explicit registry records, invalidation results, graph edges, snapshots, and readiness metadata.

Final validation for this V1 change set passed: prohibited Engineering Intelligence boundary scan exit code `0`, topology guard exit code `0`, TypeScript check exit code `0`, full test suite exit code `0` with 147 test files and 4,859 tests passing, production build exit code `0`, and lint exit code `0`. Build and test logs contain expected environment warnings for unset runtime variables in the sandbox; these did not fail validation.
