## 1. Purpose

This policy is the rule for **what we encrypt, how we encrypt it, where the keys live, who can touch them, how often we rotate them, and what we do when one is compromised**. It's the **SOC 2 CC6.1 + CC6.7 + ISO 27001 A.5.17 + A.8.24 + ISO 27017 A.8.24** evidence: that Solarpro uses cryptography proportionate to the data it protects, that the cryptographic posture is auditable, and that the rules are enforced in code — not in tribal knowledge.

The Password & Authentication Policy (#15) covers the **user-facing** authentication rules (12+ char passwords, MFA, lockout). This policy covers the **machine-facing** cryptography: the JWT signing secret, the database password, the API keys, the HMAC webhook secrets, the MFA TOTP encryption key, the TLS certificates, and the in-app symmetric keys that protect structured data at rest.

The rules below were not invented in 2026. They were already in the codebase as a series of one-off checks (`getJwtSecret()`, `lib/survey/handoff/tokenMinter.ts:112`, `lib/mobile/auth.ts`) and as the operational practice of the engineering team. The 2026-07-30 security quickwins PR (commit `3b9db2cbc`) made the 32-character minimum for `JWT_SECRET` a runtime check at boot. This policy codifies that check — and the broader key management discipline — so the rules cannot regress, and so an auditor sees one document instead of grepping the repo.

The 3-person team constraint is real. The policy is written so a single engineer (Cody) can implement it, a single CISO (Raymond) can audit it, and a single CEO (James) can sign off on the risk acceptance — with no specialized tooling beyond 1Password, the cloud provider's secret store, and the standard CLI utilities (`openssl rand`, `openssl s_client`).

## 2. Principles

Five principles, in priority order.

1. **Encrypt by default.** If data is stored, transmitted, or processed by Solarpro, it is encrypted at rest and in transit. The only exception is data that is intentionally public (the marketing site, the public Trust Center, the public API documentation), and that exception is enumerated in the Data Classification & Handling Policy (#03), not implied.
2. **The key is not the password.** User passwords are user-chosen and meet the §3 rules in Policy 15. Machine credentials are 32+ characters of high-entropy randomness, generated by a cryptographically secure source, and never typed by a human. A 32-character hex string is more entropy than any human-generated passphrase and is the standard for high-value machine credentials.
3. **The cloud provider does the heavy lifting.** Solarpro runs on Vercel, Neon, Render, Cloudflare, GitHub, Google Workspace, Stripe, and Resend. Every Tier 1 vendor already provides encryption at rest and in transit with documented key management. The policy leverages those vendor capabilities; it does not duplicate them. Solarpro's job is to (a) verify the vendor's posture, (b) configure the vendor correctly, and (c) add Solarpro-side controls (the application-level keys, the HMAC webhook secrets, the MFA TOTP key) that the vendor does not own.
4. **Keys are rotated on a schedule AND on events.** Calendar-based rotation catches the case where a key was compromised but nobody noticed. Event-based rotation (personnel change, suspected breach, vendor incident) catches the case where the calendar is too slow. Both are required.
5. **A compromise is loud, not silent.** A compromised key is rotated immediately, the audit log is reviewed, and the incident response plan (#05) is triggered. A 32-character secret does not need to "age out" before it is rotated if there is evidence it is no longer secret.

## 3. Cryptographic standards

Solarpro uses industry-standard cryptography. The standards are reviewed annually as part of the §10 review cadence and on any algorithm-deprecation announcement from NIST or the cryptographic community.

### 3.1 Symmetric encryption

- **AES-256-GCM** for application-level symmetric encryption. The `MFA_ENCRYPTION_KEY` (32 bytes / 256 bits) encrypts TOTP seeds at rest. The authenticated encryption (GCM mode) provides both confidentiality and integrity in one operation; a tampered ciphertext fails the GCM tag check and raises a runtime error.
- **ChaCha20-Poly1305** is acceptable as an alternative where AES-NI is unavailable (older or constrained devices). The application does not currently use it; the policy allows it for future use.

### 3.2 Asymmetric encryption and signing

- **RSA-2048 or stronger** (RSA-3072, RSA-4096) for asymmetric encryption. The application does not currently use RSA for application-level encryption; the standard is documented for vendor-issued certificates.
- **Ed25519** for application-level signing. Used for any future signature-on-payload use case (the engineering team has not yet needed it; the standard is documented for future use).
- **HMAC-SHA-256** for webhook signature verification. The application uses `crypto.timingSafeEqual` to compare the expected and actual HMAC values, with a 5-minute timestamp tolerance window to defeat replay attacks (see `audit_security_migrations §7` for the implementation review).

### 3.3 Hashing

- **SHA-256 or stronger** (SHA-384, SHA-512) for any hashing use case.
- **bcrypt with cost factor 12** for password storage. The `users.password_hash` column in Neon. The cost factor is verified at the next password change.
- **MD5 and SHA-1 are forbidden.** The application does not use either. The vendor libraries that do (older SSL cert chains, some S3 SDK paths) are tracked in the dependency advisory and replaced when a vendor fix is available.

### 3.4 TLS

- **TLS 1.2 or higher** for all external traffic. The application is HTTPS-only; HTTP requests are redirected to HTTPS at the Vercel edge.
- **TLS 1.3** is the preferred version for new integrations. Cloudflare, Vercel, and Render all default to TLS 1.3 on the edge; the application does not need to opt in.
- **mTLS** is documented as the preferred pattern for service-to-service authentication where the service is not behind a session boundary. Today, all internal service-to-service auth is HMAC (webhooks) or a long-lived service account (CI/CD). A future move to mTLS is recorded in the Cloud Services Security Policy (#24).

## 4. Data at rest

Encryption of data at rest is **inherited from the cloud provider** plus **enforced at the application level** for the few cases where the provider does not cover it. The combined posture is the audit evidence.

The disk is ephemeral (the container is replaced on every deploy); model weights are in the deploy artifact, which is the source of truth. | The ONNX INT8 model artifacts are checked into git (size-permitting) or stored in the deploy bundle; they are not separately encrypted. The model is not PII. | Render's SOC 2 Type 2 report |
| **Application user passwords** | Neon (the `users` table) | Inherits Neon's AES-256 at rest. | **bcrypt with cost factor 12** at the application level. The plaintext is never stored, never logged, never returned by any API. | `lib/auth.ts` (the registration and login routes) |

| **JWT signing** | Application memory (in process) | n/a (in-memory only). | HS256 with the `JWT_SECRET` (32+ char). The secret is never logged; it is loaded from the environment at boot. | `lib/auth.ts:getJwtSecret()` |

The provider-level encryption is **inherited**, not re-asserted by Solarpro. The application-level encryption is **enforced and audited**. The combination is what the auditor evaluates.

|---|---|---|---|

| **Webhook sources (Stripe, survey, Meta, Google, generic) → Vercel** | TLS 1.2+ (HTTPS). | HMAC-SHA-256 signature verification with `crypto.timingSafeEqual` + 5-minute timestamp tolerance + idempotency key on `webhook_deliveries.event_id`. | `app/api/webhooks/*` |

| **Email (Resend → recipient inbox)** | TLS 1.2+ (recipient inbox is responsible for the receiving side; Resend enforces TLS on the sending side via MTA-STS). | DKIM + SPF + DMARC on the `solarpro.app` domain. | Resend dashboard + DNS at Cloudflare |

The pattern: **TLS everywhere, HMAC or API key for authentication of the application layer.** The application does not implement custom encryption on the wire beyond what the platform and the standards provide.

## 6. Key types and rotation

The application has a finite inventory of high-value keys. Each has a documented owner, rotation cadence, and storage location. The full key inventory is in the application env-fingerprint artifact at `compliance/monitoring/env-fingerprint-<date>.json` (the manifest at `compliance/manifest.json` §"env-fingerprint" defines the schema); the policy summarizes the rules.

### 6.1 JWT signing secret (`JWT_SECRET`)

- **Algorithm**: HS256. The secret signs and verifies every JSON Web Token issued by the application.
- **Length**: **minimum 32 characters** of high-entropy randomness, generated by `crypto.randomBytes(32).toString('hex')` (Node) or `openssl rand -hex 32`. The minimum is enforced at boot by `getJwtSecret()` (per the 2026-07-30 security quickwins PR). A shorter secret causes the application to refuse to start.
- **Storage**: Vercel encrypted env var (production). Local `.env.local` (development, never committed). 1Password team vault (for sharing with the team and for the rotation ritual).
- **Rotation cadence**: **annually** (the next rotation is due 2027-08-15), OR on any suspected compromise, OR on the departure of anyone with access. The rotation forces the invalidation of all outstanding tokens (the `iat` cutoff).
- **Compromise response**: rotate immediately, audit log review, incident response per Policy 05.

### 6.2 Database credentials (`DATABASE_URL`)

- **Algorithm**: TLS in transit, native Postgres `md5` or `scram-sha-256` password authentication.
- **Length**: Neon issues a 32+ character random password for the production database role. The development database (local Docker) uses a short password because it is not network-accessible.
- **Storage**: Vercel encrypted env var. Neon project settings (the password is set there, not visible after entry).
- **Rotation cadence**: **quarterly**, OR on the departure of anyone with database access, OR on any suspected compromise. The rotation is coordinated with Neon (the password change invalidates all current connections; the application reconnects with the new password).
- **Compromise response**: rotate immediately, audit log review (`pg_stat_activity` for any active sessions, the audit_log table for any recent privileged queries), incident response per Policy 05.

### 6.3 API keys (third-party)

- **Algorithm**: TLS in transit, API key in the `Authorization: Bearer <key>` header (or in the `api_key` query parameter, per the vendor's convention).
- **Length**: per the vendor's policy. Stripe, OpenAI, Anthropic, Resend, Sentry, Nearmap, Eagleview, Google Solar, ATTOM all issue keys of at least 32 characters.
- **Storage**: Vercel encrypted env var. GitHub Actions encrypted secrets (for CI-only keys, e.g. the Sentry deploy token).
- **Rotation cadence**: **per the vendor's recommendation** (most vendors recommend annual or "as needed"). Solarpro's default is annual, on the same anniversary as the JWT secret rotation, unless the vendor recommends a different cadence.
- **Compromise response**: rotate immediately, audit log review (the vendor's usage logs are the primary signal), incident response per Policy 05.

### 6.4 API keys (Solarpro-issued, to mobile clients and CI)

- **Algorithm**: HMAC-SHA-256 or Bearer token, depending on the consumer.
- **Length**: 32+ characters, generated by `crypto.randomBytes(32).toString('hex')` or the 1Password generator.
- **Storage**: Vercel encrypted env var (the public key) and 1Password team vault (the private key). Mobile clients receive the key via a secure channel (App Store / Play Store encrypted bundle, or a 1Password shared item).
- **Rotation cadence**: **annually**, OR on the departure of anyone with access, OR on any suspected compromise.
- **Compromise response**: rotate immediately, audit log review (the `audit_log` table for any use of the compromised key), incident response per Policy 05.

### 6.5 MFA TOTP encryption key (`MFA_ENCRYPTION_KEY`)

- **Algorithm**: AES-256-GCM. The key encrypts every TOTP seed at rest.
- **Length**: **32 bytes (256 bits)**, generated by `crypto.randomBytes(32).toString('hex')` and stored as a 64-character hex string.
- **Storage**: Vercel encrypted env var. 1Password team vault.
- **Rotation cadence**: **annually**, OR on any suspected compromise. The rotation requires re-encrypting every TOTP seed in the database; the rotation is a planned maintenance window (the users are re-enrolled in MFA via the standard enrollment flow).
- **Compromise response**: rotate immediately, force re-enrollment for all MFA users, audit log review, incident response per Policy 05.

### 6.6 Webhook signing secrets (`SURVEY_WEBHOOK_SECRET`, etc.)

- **Algorithm**: HMAC-SHA-256. The secret signs every outbound webhook payload; the receiver verifies with the same secret.
- **Length**: 32+ characters, generated by `crypto.randomBytes(32).toString('hex')`.
- **Storage**: Vercel encrypted env var (the sender side). The receiver side is documented in the integration's `README.md` and stored in the receiver's secret store.
- **Rotation cadence**: **annually**, OR on any suspected compromise. The rotation is coordinated with the receiver (a brief window during which both old and new secrets are accepted; the receiver is given a 24-hour heads-up).
- **Compromise response**: rotate immediately, audit log review of the webhook delivery log, notify the receiver, incident response per Policy 05.

### 6.7 Session cookies

- **Algorithm**: HttpOnly + Secure + SameSite=Strict cookies. The session is server-side (the cookie holds a signed JWT, verified on every request).
- **Length**: the cookie value is the JWT, which is bounded by the payload size (typically 200-400 bytes).
- **Storage**: browser cookie store. The `Secure` flag is set on production cookies (per the security quickwins PR's `isProduction()` fix); the `SameSite=Strict` flag is set on all cookies.
- **Rotation cadence**: not rotated (the cookie is short-lived; the user re-authenticates per Policy 15 §7).
- **Compromise response**: invalidate the user's session via `password_changed_at` (Policy 15 §7.4); force re-authentication.

### 6.8 TLS certificates

- **Algorithm**: TLS 1.2+ (TLS 1.3 preferred). Certificates are managed by the edge (Vercel + Cloudflare).
- **Length**: RSA-2048 or ECDSA P-256.
- **Storage**: Vercel edge (managed); Cloudflare edge (managed). Solarpro does not hold the private keys.
- **Rotation cadence**: **automated by the edge** (Let's Encrypt via Vercel rotates every 60-90 days; Cloudflare rotates its origin certificates on a similar cadence). Solarpro's job is to verify the rotation and to renew the Cloudflare origin certificate when Cloudflare sends a renewal notice.
- **Compromise response**: Cloudflare and Vercel both have 24/7 support for certificate incidents. A compromised edge certificate is a Sev1 incident.

### 6.9 The rotation table

A summary of the rotation rules. The "Triggers" column lists the event-based rotation conditions.

| Key | Length | Storage | Calendar rotation | Triggers |
|---|---|---|---|---|
| `JWT_SECRET` | 32+ chars | Vercel env var, 1Password | Annual | Compromise, personnel departure |
| `DATABASE_URL` password | 32+ chars | Vercel env var, Neon | Quarterly | Compromise, personnel departure |
| Third-party API keys | Vendor-issued | Vercel env var, 1Password | Annual (or per vendor) | Compromise, vendor incident |
| Solarpro-issued API keys | 32+ chars | Vercel env var, 1Password | Annual | Compromise, personnel departure |
| `MFA_ENCRYPTION_KEY` | 64 hex chars (32 bytes) | Vercel env var, 1Password | Annual | Compromise, force re-enrollment |
| Webhook HMAC secrets | 32+ chars | Vercel env var, 1Password | Annual | Compromise, receiver notification |
| Session cookies | (JWT, ~200-400 bytes) | Browser cookie store | n/a (re-auth on policy 15 §7) | `password_changed_at` invalidation |
| TLS certificates | RSA-2048+ | Edge (managed) | Auto (60-90 days) | Vendor incident |

## 7. Key storage rules

The principle: **the key is never in a place that can leak.** The places that can leak are the source code repository, Slack, email, screenshots, unencrypted local files, and the browser password manager (for machine credentials). The places that cannot leak (within reason) are the cloud provider's secret store, 1Password, and the local `.env.local` (which is in `.gitignore` and never committed).

### 7.1 GitHub Actions encrypted secrets

CI/CD uses GitHub Actions encrypted secrets. The secret is injected at job time via `${{ secrets.NAME }}`. The secret is not visible in the workflow logs (the value is replaced with `***` in the GitHub UI). The rotation is via the GitHub UI.

### 7.2 Vercel encrypted env vars

Production uses Vercel encrypted env vars. The secret is set via the Vercel dashboard; the value is not visible after entry (only "rotate" is exposed). The rotation is via the Vercel dashboard or the Vercel CLI.

### 7.3 Render encrypted env vars

The SAM2 service uses Render encrypted env vars. Same posture as Vercel: the value is not visible after entry.

### 7.4 Neon project secrets

Database passwords and API tokens are set in the Neon project settings. The value is not visible after entry.

### 7.5 1Password team vault

The team vault is the human-readable secret store. Secrets are stored as 1Password items with restricted access (only the people who need to know). The 1Password team admin role is restricted to Raymond and James; the team can request access via the standard 1Password provisioning flow.

### 7.6 Forbidden storage locations

- **Source code**: a secret in `package.json`, a config file, a comment, a test fixture, or anywhere else in the git repo is a Sev1 incident. The commit is reverted; the secret is rotated; a postmortem is filed.
- **Slack / email / screenshots**: a secret in any of these is a Sev1 incident. The message is deleted; the secret is rotated; the recipients are notified.
- **Browser password manager**: machine credentials (32+ char random strings) are not memorable; they do not belong in the browser password manager. User passwords (12+ char passphrases) are fine in 1Password.
- **Unencrypted local files**: `.env.local` is the only allowed local file, and it is in `.gitignore`. A `.env` file (no `.local`) is a security incident.
- **Public buckets, public S3-compatible storage, public Vercel Blob containers**: a public bucket is a misconfiguration, not a key storage location. The Cloud Services Security Policy (#24) §5 covers the weekly config-drift check.

## 8. Key compromise response

A compromised key is a Sev1 incident. The response is the same regardless of the key.

1. **Rotate the key immediately.** The rotation is logged in `compliance/secrets-rotation/<key>-<date>.md` with the actor, the date, the reason, and the new key's fingerprint (the first 8 characters of the SHA-256 hash, for verification).
2. **Review the audit log.** The relevant log is the `audit_log` table in Neon, plus the vendor's usage log if the key is a third-party API key. The review is documented in the incident file.
3. **Trigger the Incident Response Plan (#05).** The IR plan is the operational rule for the rest of the response (containment, eradication, recovery, postmortem).
4. **Notify the affected parties.** If customer data is involved, notify per the Privacy Policy (#18) §9 and the Data Subject Rights Policy (#19) for the breach-notification runbook. If a vendor is involved, notify the vendor.
5. **Update the key inventory.** The next rotation date is reset; the trigger that caused the compromise is added to the §6.9 table as an additional trigger.

A key compromise that is not handled per the §8 steps is a violation of this policy and is escalated per the Information Security Policy (#01) §9.

## 9. The 90-day admin expiry

The Access Control Policy (#03) §5.2 sets the **90-day admin expiry**: any `super_admin` or `admin` grant expires after 90 days by default and requires a Linear issue with James's approval to renew. The expiry is enforced by `auditLog.ts` and the quarterly User Access Review (UAR).

This policy references the 90-day rule because the **90-day expiry cascades into the key management rules**: when a person's admin grant expires, their access to the keys in 1Password, the Vercel env vars, the GitHub Actions secrets, and the cloud provider consoles is reviewed. If the access was tied to the admin role, the access is revoked at the same moment the admin role expires. The two policies are coordinated.
