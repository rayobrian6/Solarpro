# Equipment-identity chain audit — 26 verified bypasses

Produced for the fifth item of the burn-down directive: *"find and verify the existing
manufacturer specs → compatibility authority → topology authority → equipment-instance
authority → downstream consumers, repair bypasses rather than inventing another solver."*

This is a **verification of the existing authority**, not a discovery campaign. Every agent was
asked one question — does this consumer honour `lib/equipment-db.ts`, or bypass it — and told
to report an empty list rather than pad.

**Six consumer boundaries, 34 findings raised, 26 survived.** Each survivor was attacked by two
independent skeptics with different lenses (*does the mechanism actually run* / *is the
authority really bypassed*), each instructed to default to REFUTED when it could not confirm
the claim from the code. **8 were killed that way**, and several survivors were materially
amended — read the *What verification corrected* paragraph before acting on any of them.

> 🚨 **A HEADING HERE IS THE CLAIM AS RAISED, NOT A VERIFIED FACT.** Where verification amended
> the numbers, the heading is left as the auditor wrote it and the correction follows
> underneath, so the two can be compared. #8's "28 of the 33" is really **31 of 33**, and its
> direction is two-way rather than under only.

🚨 **NOTHING HERE IS FIXED.** The 19 are done; this is the queue that replaces them. It is
recorded before touching any of it because several fixes change **what a homeowner is quoted or
what a signed document says** — that is Ray's call, not a unilateral edit. The pricing basis it
turns on is now R17 in `NEEDS-RAY.md`.

**23 peer-owned files were excluded**, so this list is not exhaustive for `bom-engine-v4.ts`,
`computed-system.ts`, `page.tsx`, the permit sections or the SLD renderer.

## Pricing

### 8. Panel cost is a flat $0.50/W for 28 of the 33 catalogued modules, and the wattage is parsed out of a DISPLAY STRING instead of read from equipment-db

`lib/bom/distributorPricing.ts:840` — **⬇ UNDER-states the true value** · raised at high confidence

**Authority bypassed.** lib/equipment-db.ts SOLAR_PANELS — `panelId` IS the module identity and each entry publishes `watts` (e.g. line 344-348 `id: 'rec-alpha-pure-430' … watts: 430`). This consumer reads neither. It resolves the module's wattage by regex over `item.model + item.description` (display text), and it resolves the module's PRICE from a hardcoded $0.50/W literal that is blind to which product was chosen. A second panel-wattage catalogue also exists in the same file at :728-734 (`PANEL_WATTAGE_BY_PART`), duplicating `watts` for 5 SKUs.

**Mechanism.** DISTRIBUTOR_PRICE_CATALOG carries 5 solar_panel rows (:126, :135, :145, :152, :159) against 33 entries in equipment-db SOLAR_PANELS. The BOM line's partNumber is the uppercased equipment-db id — the file says so itself at :141-144 ("Alias for the equipment-db id ('rec-alpha-pure-405' → uppercased) the BOM engine emits") and lib/system/sizingToBom.ts:107-134 does the same (`partNumber: inv.id` / `micro.id` / `opt.id` / `bat.id`), with both sides uppercased at :756 and :813. Pick REC Alpha Pure-R 430W (`rec-alpha-pure-430`, an HJT premium module, equipment-db:344-355): lookup key `REC-ALPHA-PURE-430` misses the catalog, no category override exists, so line 840 parses "430W" out of the model string and returns 0.50 × 430 = $215.00/panel. Its own 405 W sibling `REC-ALPHA-PURE-405` has a row at :145-149 stating `netPrice: 0.98` with the comment at :133-134 "dealer ~$0.95–1.0/W (~$385–486/panel), NOT the ~$0.37/W commodity rate previously assumed" — i.e. the correct figure is ~$421/panel. On a 24-module 10.3 kW array the module line reads $5,160 instead of ~$10,100: $4,944 missing. The repair for the 405 W variant was a hardcoded id literal, so it did not reach the 430 W variant of the same product. The string parse is also independently lossy: `panel-cs3`-class model text "BiKu CS3W-440PB (Fence)" yields no `\d{3,4}\s*W` match ('3W' is one digit, '440PB' is followed by P), so a 440 W module falls through to `fallback.unitCost` = 0.50 × 400 = $200.

**Artefact.** `pricing.totalBomCost` returned by app/api/engineering/bom/route.ts:794 (the "Est. Hardware Cost" / "$/W" figures) and the Unit Cost / Total Cost columns of the archived `BOM_<project>.csv` written by app/api/engineering/save-outputs/route.ts:571-595 — the file the purchaser actually orders from. The installer quotes at the $/W sell price believing a margin that is ~$5k larger than it is.

**What verification corrected.** Three corrections; the core defect stands.

1. It is 31 of 33, not 28 of 33. Only `rec-alpha-pure-405` (alias row, distributorPricing.ts:145-149) and `panel-fence-ps1` (equipment-registry-v4.ts:255, partNumber PS-MNB108-HCBF-440W) ever reach a priced catalog row. The other 31 catalogued modules all land on line 840.

2. The display-string parse is real but is NOT the thing that produces the wrong number, and the claim's counter-example is refuted. bom-engine-v4 writes `description = `${panelDb.watts}W Solar Panel`` straight from equipment-db `watts`, so the regex over `${item.model} ${item.description}` recovers the correct wattage on every live path. For `panel-fence2` the concatenated string is "BiKu CS3W-440PB (Fence) 440W Solar Panel" — the regex skips "CS3W" (one digit) and "440PB" (no W) and matches "440W" in the description, giving w=440 → $220.00, not the claimed $200 flat. The parse only actually fails in two places, and neither is the claimed one: (a) the no-panel-selected line (model "Solar Panel (specify model)", description "Solar Panel") → no match → NaN → flat `CATEGORY_FALLBACK_PRICES.solar_panel` = 0.50 × 400 = $200.00 at :843; (b) `resolveUnitCost` (:934-953), whose fixture sets `model: ''` and `description: ''` — but its only production caller, app/api/admin/distributor-prices/route.ts:118, passes just the 5 catalog partNumbers, all of which hit step 3, so that path is dead.

3. The bypass is not "it failed to read a price from equipment-db" — equipment-db publishes no price (the SolarPanel interface at equipment-db.ts:6-39 has `watts` but no cost field). The bypass is that the $0.50/W literal is blind to which `panelId` was chosen: the module identity never reaches the price at all, and the file's own per-product authority (:131-134) was wired to two hardcoded id literals instead of the id.

Consequence of (3): the direction is TWO-WAY, not one-way under. Premium modules are under-specified (REC 430 → $215 vs ~$421; Maxeon/Tesla likewise). Large commodity bifacials are OVER-specified: `cs-hiku7-600` (equipment-db:410-414, watts 600) → 0.50 × 600 = $300.00/panel, against the ~$0.37/W commodity band this same file cites at :132-134, i.e. roughly $80–130/panel of phantom cost per module in the same `BOM_<project>.csv` and the same Est. Hardware Cost tile. Both errors are wrong dollar figures in the document the purchaser orders from, and neither is disclosed there — `buildBomCsv` (save-outputs/route.ts:571-573) has no source or basis column, so the `source: 'fallback'` marker that `applyDistributorPricing` computes never reaches the human.

### 9. The price the homeowner sees is computed from panels only — adding a battery changes the BOM by thousands and the customer's System Cost by $0

`lib/pricingEngine.ts:261` — **⬇ UNDER-states the true value** · raised at high confidence

**Authority bypassed.** "An equipment choice must reach every artefact identically: Engineering = Diagram = SLD = Permit = Equipment Schedule = BOM = Pricing = Saved Project." `batteryId` is a first-class equipment choice — it is a V4-owned BOM category (app/api/engineering/bom/route.ts:40), it is driven by `batteryEnabled` / `targetBatteryKwh` (bom/route.ts:660-662), and equipment-db BATTERIES publishes 30 units with `usableCapacityKwh` and `msrpUsd`. The customer-price chain never receives it: the ONLY equipment input to the price is an array of panels.

**Mechanism.** app/api/production/route.ts:136-137 `const itemized = calculateItemizedPrice(panels, layoutType, pricingCfg); const cashPrice = itemized.totalCashPrice;` — panels only; the returned `costEstimate` is persisted (route.ts:563, :693). app/proposals/view/[id]/page.tsx:428 and app/api/proposals/[id]/pdf/route.ts:233 read it back as `storedCashPrice: costEstimate?.cashPrice ?? costEstimate?.grossCost ?? 0`. lib/proposal/buildCanonicalProposal.ts:639 `const baseCashPrice = input.storedCashPrice > 0 ? input.storedCashPrice : liveCalculatedPrice` (:638 `liveCalculatedPrice = systemSizeW * livePpw`, where `systemSizeW` is PV DC watts), :642 `effectiveFinal = baseCashPrice`, :924-925 `gross_system_cost: effectiveFinal, systemCost: effectiveFinal`. lib/proposal/renderProposalHTML.ts:462-463 renders it as the headline "System Cost", and :493 as "Gross System Cost". Grepping `batter|storage` across app/api/production/route.ts and lib/proposal/buildCanonicalProposal.ts returns no price term at all, and there is no `batteryPrice` / `batteryCost` / `pricePerKwh` / `batteryAdder` symbol anywhere in lib/ or app/. So: design 20 × 440 W roof + one Tesla Powerwall 3. `totalBomCost` rises by $8,280 (the catalog row at distributorPricing.ts:498-502) — or by $4,200 via the category fallback for the other 27 batteries. The homeowner's "System Cost" is 20 × $1,364 + $2,000 = $29,280 with the battery and $29,280 without it. The same proposal simultaneously advertises storage incentives to that homeowner (renderProposalHTML.ts:756-757 `prog.battery_incentives`, "Battery Rebate" / "VPP"), so the battery is present in the document and absent from its price. The sanctioned override that could have patched this by hand was removed from the contract (production/route.ts:106-119, "Nothing in the repo sends it").

**Artefact.** The homeowner-facing proposal PDF and share view — "System Cost" (lib/proposal/renderProposalHTML.ts:463) and "Gross System Cost" (:493), plus every number derived from it: netCost, payback years, 25-yr net difference, and the ITC basis at :670. The installer sells and installs the battery for free.

**What verification corrected.** The core claim holds unchanged. Two supporting details in the stated mechanism are wrong, and correcting them makes the defect broader, not narrower.

WRONG #1 — the storage-incentive table is not evidence the battery is in the document. The claim says "The same proposal simultaneously advertises storage incentives to that homeowner (renderProposalHTML.ts:756-757 `prog.battery_incentives`), so the battery is present in the document and absent from its price." That inference does not hold. At renderProposalHTML.ts:737 `const prog = cp.policy.utilityPrograms`, sourced from lib/utilityPrograms.ts:4680 `battery_incentives: batteryProgs` — keyed by UTILITY, not by the design. The whole block is gated only on `cp.policy.utilityPrograms` existing (:736). A PV-only design on the same utility prints the identical "Battery Rebate" / "VPP" rows. So this is not a battery-present-vs-battery-unpriced contradiction; it is utility policy boilerplate.

WRONG #2 — and this is the real finding: the battery is absent from the proposal ENTIRELY, price AND equipment. `grep -ni "batter|storage|powerwall|backup"` across lib/proposal/renderProposalHTML.ts returns only the four utility-program lines (:751, :752, :756, :757). The PDF's Equipment pages (`pageEquipment`, :813-844, and the summary table :404-406) emit Solar Panel and Inverter rows only — there is no battery row to emit. The one place a battery could surface is the share view's "System Equipment" card: app/proposals/view/[id]/page.tsx:1926-1929 (mirrored at app/proposals/page.tsx:2964-2967) feeds `deriveEcosystemSummary({ ..., batteries: (proj as any)?.selectedBattery ? [...] : [] })`. That branch is DEAD: no producer anywhere sets `selectedBattery`. The hydration layer declares and fills only two fields — lib/db/core.ts:291-292 `selectedPanel?` / `selectedInverter?`, populated at :314-315 and :353-354, mirrored in lib/db/production.ts:18-19/:28-29/:278-279 and lib/db/projects.ts:62-66/:89-90. `selectedBattery` is not in that interface at all, so `(proj as any).selectedBattery` is always `undefined` and the batteries array is always `[]`.

CORRECTED MECHANISM. Design 20 × 440 W + Tesla Powerwall 3. `batteryId` persists to `projects.selected_equipment` under the I-5 mirror invariant (lib/db/projects.ts:527-534). The BOM, SLD, permit and equipment schedule all carry it; `totalBomCost` rises $8,280 (lib/bom/distributorPricing.ts:499) or $4,200 via the category fallback (:689). The proposal chain receives it nowhere: `calculateItemizedPrice`'s only equipment parameter is `panels` (lib/pricingEngine.ts:261), so `costEstimate.cashPrice` is $29,280 either way, and that single number is the sole price input to buildCanonicalProposal (:639). The result is not "the battery is in the document but not in its price" — it is that the homeowner-facing proposal is silently a PV-only document for a PV+storage design: the battery appears in neither the "System Cost" nor the equipment list, while the BOM the installer buys from includes it. Pricing and BOM disagree about the same design's equipment, and the proposal gives the homeowner no visible cue that anything is missing — which is what makes it unlikely to be caught by a rep reading the PDF.

### 10. Every battery is $4,200 flat regardless of which battery — a 3.4 kWh unit and an 18.5 kWh unit cost the same, while equipment-db publishes msrpUsd for all 30

`lib/bom/distributorPricing.ts:689` — **⇄ INCONSISTENT — two artefacts disagree about one design** · raised at high confidence

**Authority bypassed.** `BatterySystem.msrpUsd` is a REQUIRED field on the canonical authority (lib/equipment-db.ts:2695 `msrpUsd: number;`), populated for all 30 BATTERIES entries, alongside `usableCapacityKwh` (:2646). This consumer reads neither — no capacity branch exists for `battery` the way one does for `solar_panel` at :839-841. Device cost is inferred from a CATEGORY string rather than from the product's published price or capacity. The only consumer of `msrpUsd` anywhere in the repo is lib/engineering/generatorData.ts:86; the BOM pricing path never touches it.

**Mechanism.** DISTRIBUTOR_PRICE_CATALOG holds 3 battery rows (`IQ-BAT-5P-1P-240`, `PW3-US`, `EF-BATT-5K-LFP`, :491-506) against 30 entries in equipment-db BATTERIES. Any other battery misses `getCatalogByPartNumber()` at :826-832 and lands on this line. Measured against equipment-db's own published prices: `generac-pwrcell-17` (17.1 kWh, msrpUsd 14000) → $4,200, understated $9,800; `bat-fp1` (18.5 kWh, msrpUsd 14500) → $4,200, understated $10,300; `bat-lg1` (16.0 kWh, msrpUsd 12500) → understated $8,300; `franklin-apower-15` (15.0 kWh, msrpUsd 10500) → understated $6,300. The error also flips sign on small units: `enphase-iq-battery-3t` (3.36 kWh, msrpUsd 2800) → $4,200, overstated $1,400; `ecoflow-battery-5kwh` (msrpUsd 2800) → overstated $1,400. So the BOM total moves in whichever direction the operator did NOT choose the battery for, and a capacity upgrade from a 9 kWh to a 17 kWh unit changes the hardware cost by exactly zero. Same shape, smaller dollars, on `gateway` (:711 `{ unitCost: 690.00 }`, commented "standalone IQ Gateway ~$690") which contradicts equipment-db `enphase-iq-gateway.msrpUsd: 450` (:4056) for the identical product — a dealer NET above the manufacturer's MSRP.

**Artefact.** `pricing.totalBomCost` (app/api/engineering/bom/route.ts:794) — the Est. Hardware Cost and $/W figures the estimator prices a storage job from — and the Unit Cost / Total Cost columns of `BOM_<project>.csv` (app/api/engineering/save-outputs/route.ts:571-595) the purchaser orders against. On a whole-home backup job the installer under-recovers ~$10k per large battery; on a small-battery job it inflates its own cost basis by ~$1.4k.

**What verification corrected.** There IS a real identity-shape mismatch, but it is currently inert and it is not the one claimed. `lib/system/sizingToBom.ts` resolves battery identity out of the CANONICAL catalogue and then stamps the canonical id where a distributor SKU belongs: `enrichFromEquipmentDb` at `:128-135` returns `partNumber: bat.id` from `getBatteryById(equipmentDbId)`, and the battery emission at `:229-250` uses `partNumber: enriched.partNumber ?? sizing.battery.equipmentDbId`. The value is therefore always an equipment-db id (`'bat-fp1'`, `'generac-pwrcell-17'`, or even `'tesla-powerwall-3'`), and `DISTRIBUTOR_PRICE_CATALOG`'s key space is distributor SKUs (`'PW3-US'`), so a catalog hit is impossible by construction — including for the Powerwall 3, whose real $8,280 net exists in the catalog under a different string. Feed that item to `resolvePriceForItem` and it lands on `lib/bom/distributorPricing.ts:689` at $4,200.

It never gets there today. `app/api/engineering/bom/route.ts:40` puts `'battery'` in `V4_OWNED_CATEGORIES`, so `injectStructuralIntoV4`'s filter at `:105-108` discards the adapter's battery candidate unconditionally, and `:619-622` discards it a second time whenever V4 emitted its own battery line. The same is true of `'gateway'` (`:44`) and `'monitoring_gateway'` (`:54`), so the adapter's gateway candidates (`partNumber` = `component.equipmentDbId`, `sizingToBom.ts:165`, since `enrichFromEquipmentDb` has no gateway lookup at all) are dead for the same reason. The exposure is latent: delete `'battery'` from that set — or route adapter items around `injectStructuralIntoV4` — and every sizing-engine battery, the Powerwall 3 included, silently reprices to $4,200 in `pricing.totalBomCost` and in the purchaser's `BOM_<project>.csv`. The fix is to make the adapter carry the distributor SKU (or to give `resolvePriceForItem` a canonical-id lookup), not to add a capacity branch beside the `solar_panel` one at `:839-841`.

Separately, and out of scope here: the plausible live defect in this area is not a mispriced battery line but a MISSING one. The engineering UI sends equipment-db ids (`lib/permit/utils/computedRuns.ts:156` notes `batteryIds: [config.batteryId]`), `EQUIPMENT_REGISTRY_V4` knows 3 of the 30 `BATTERIES`, and `tests/bomBackfeedCountsTheBattery.test.ts:224-232` shows `generateBOMV4` accepts `batteryId: 'battery-that-is-not-real'` without error. Whatever happens to the other 27 batteries' line items happens inside `lib/bom-engine-v4.ts`, which is excluded from this audit — that is where the question should be re-asked once that file settles.

## Proposal / customer document

### 1. Signed proposal claims a 30-year PRODUCT warranty on a module whose product warranty is 12 years

`app/proposals/view/[id]/page.tsx:1967` — **⬆ OVER-states the true value** · raised at high confidence

**Authority bypassed.** lib/equipment-db.ts is the one equipment catalogue and publishes the module's warranty as a two-part datasheet term: line 518, `warranty: '12yr product / 30yr linear power'` for id `panel-fence-ps1`. The proposal never calls getPanelById(selectedPanel.id) - the id is present in the snapshot (lib/db/core.ts:314 hydrates `selEq.panel`, which carries `id`) - and instead reads the collapsed single number from the SECOND catalogue, lib/db.ts:241, `warranty: 30,   // 30-year linear power warranty (12-year product warranty)`. lib/equipment-library.ts:118 makes the shadowing explicit: `warranty: libPanel?.warranty ?? (parseInt(p.warranty) || 25)` - the db.ts number (30) wins over the parsed datasheet product term (12).

**Mechanism.** A Sol Fence design picks panel-fence-ps1. The Design Studio seeds selectedPanel from lib/db.ts defaultPanels, so the saved project carries `warranty: 30`, which is the LINEAR POWER term. app/api/proposals/route.ts:194 snapshots that project into the proposal. The homeowner share view then renders the string `30-yr product warranty` with a green checkmark beside it, on the page carrying the Sign & Accept button. The module's actual product warranty is 12 years. The exact same substitution hits every panel whose two terms differ: e.g. a 'hyundai' or mono-PERC entry recorded as '12yr product / 25yr power' presented as a 25-yr product warranty.

**Artefact.** The System Equipment panel card on the customer-facing proposal share view (app/proposals/view/[id]/page.tsx) - the document the homeowner signs, and the same card on the internal builder at app/proposals/page.tsx. The installer inherits an 18-year product-warranty obligation the manufacturer does not carry.

**What verification corrected.** The claim is real; three corrections to the stated mechanism, one of which widens it a lot.

1. WIDER THAN SOL FENCE — the DEFAULT panel is also wrong. The claim frames this as a panel-fence-ps1 / SolFence case. It is not: components/design/DesignStudio.tsx:1997-1999 auto-selects `d.data.panels[0]` whenever `!project.selectedPanel`, and panels[0] is the db.ts library head, `panel-std440` "Jinko Eagle Neo N-type 440W" (lib/db.ts:54-57, `warranty: 30`). equipment-db's entry for the same id is lib/equipment-db.ts:572 `warranty: '25yr product / 30yr power'`. So the merge at equipment-library.ts:118 yields 30 and the signed card prints "30-yr product warranty" against a 25-yr product term on essentially EVERY proposal whose designer never opened the panel picker — not only fence designs. panel-fence-ps1 (30 vs 12) is merely the worst instance; hyundai-hin-nf-440 is 30 vs 25 (lib/db.ts:217 vs lib/equipment-db.ts:559).

2. THE SEEDING PATH IS THE UNIFIED MERGE, NOT defaultPanels DIRECTLY. The claim says "the Design Studio seeds selectedPanel from lib/db.ts defaultPanels". Precisely: Design Studio reads GET /api/hardware, which returns `getAllUnifiedPanels(db.getPanels())`; for an id present in both tables the record is `engPanelToUnified(engEntry, libEntry)` — equipment-db's electrical specs merged with db.ts's metadata, and it is that merge step (lib/equipment-library.ts:118) that discards the datasheet's two-part term. The persisted object is therefore a UnifiedPanel, written verbatim by app/api/projects/[id]/equipment/route.ts:55 and also by the layout/Calculate path (app/api/production/route.ts:578-580 → designEquipmentPatch, which sets `patch.panel = panel` unchanged). Either save route reaches the same wrong field.

3. THE ENGINEERING WRITE-BACK PATH SILENTLY DIFFERS — a second, independent artefact disagreement. lib/system/selectedEquipment.ts `equipmentPanelToTypesPanel()` (the engineering→design translator) emits NO `warranty` key at all. So when the panel identity is changed from Engineering (reconcileFromEngineeringConfig writes the patch only when `panel.id !== project?.selectedPanel?.id`), selected_equipment.panel loses warranty and the same card falls back to "Manufacturer warranty". Two proposals for the same physical module therefore print different warranty text depending on which app last wrote the canonical record — and this is why the defect cannot be closed by editing the label alone: the number must be resolved from getPanelById(selectedPanel.id) and split into its product / power terms at the point of render.

ADJACENT, SAME ROOT, WORTH NOTING: lib/proposal/buildCanonicalProposal.ts:391 `warranty: _fullPanelSource?.warranty ?? 25` and lib/proposal/renderProposalHTML.ts:830 `: '25 yr'` both invent a 25-year term when none is known, feeding the same collapsed single number into the canonical proposal whose own type calls it the PERFORMANCE warranty (lib/proposal/canonicalProposal.ts:57-58).

### 2. Proposal equipment schedule lists ONE inverter with no quantity, presenting a 52-micro system as 0.35 kW AC

`lib/proposal/renderProposalHTML.ts:817` — **⬇ UNDER-states the true value** · raised at high confidence

**Authority bypassed.** Device COUNT must be a conclusion of manufacturer capacity plus the actual electrical topology, never inferred from a brand or array count. Here the count is pinned at exactly 1 - one selected brand/model - and the rendered table (lines 836-851) has no quantity column at all: its headers are `#, Manufacturer, Model, Type, AC Output, Max DC V`. equipment-db publishes per-unit capacity (MICROINVERTERS carry `acOutputW`, e.g. enphase-iq8a at 349 VA max continuous, equipment-db.ts:2091-2100) which lib/equipment-library.ts:176 converts to `capacity: inv.acOutputW / 1000`; the topology (one micro per module) is never consulted.

**Mechanism.** A 52-panel design on Enphase IQ8A: selectedInverter.type = 'micro', selectedInverter.capacity = 0.349. The Equipment Specifications page of the emailed/downloaded PDF prints one row - `1 | Enphase | IQ8A | Microinverter | 0.35 kW | -` - so the schedule the homeowner signs describes a 0.35 kW AC system against a 22.9 kW DC array shown three rows above on the same page. The BOM, SLD and permit all carry 52 units / ~18.1 kW AC. The same single-slot construction also drops the per-subsystem fleet entirely: hydrateCanonicalEquipment (lib/db/core.ts:319) reads `selectedEquipmentSubSystems`, but getProjectWithDetails - the function that builds the proposal snapshot - omits it from its return (lib/db/production.ts:277-282), so a hybrid roof-Enphase + ground-SolarEdge design is presented to the customer as one inverter, the roof one, per the flat roof > ground > fence mirror.

**Artefact.** The 'Equipment Specifications' page of the proposal PDF produced by app/api/proposals/[id]/pdf/route.ts and the body of the proposal email from app/api/proposals/[id]/send-email/route.ts - the equipment schedule the homeowner signs and that a field crew or inspector may read as the agreed scope.

**What verification corrected.** Three corrections to the stated mechanism; the defect itself stands.

1. THE EMAIL CARRIES NO EQUIPMENT SCHEDULE. app/api/proposals/[id]/send-email/route.ts never imports or calls renderProposalHTML. It builds its own CanonicalProposal (`buildEmailCanonicalProposal`) and passes exactly three scalars to `sendProposalToClientEmail` — `systemSizeKw`, `annualSavings`, `netCost` (route.ts:~226-240). No inverter row, no equipment table. Drop the email from the artefact list entirely.
