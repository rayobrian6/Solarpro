## SUMMARY — transferable interaction principles

1. **The proposal is a MODE of the project, not a document produced from it.** Aurora, OpenSolar and Solargraf all render the homeowner view from the live design inside the same project chrome. Nobody rebuilds.
2. **Drift is handled by an explicit, one-click, operator-triggered REFRESH on a stable link** — never by silent auto-update and never by a new URL. Aurora: "click refresh and it's going to refresh that live link." Enerflo: a sync button *inside* the proposal that re-runs pricing too.
3. **The send button is gated on save.** OpenSolar disables "Send Proposal to Customer" with the label *"Save changes to enable send to customer."* You cannot mail a proposal that disagrees with the saved design.
4. **A persistent right rail is the whole interaction model**: SYSTEM OPTIONS → PAYMENT OPTIONS → NEXT STEP (rep photo + CTA). The homeowner switches and the entire document recomputes.
5. **Options are design CLONES, not report variants** — each carries its own shading recalculation, BOM and price.
6. **Comparison is a 2-axis matrix** (design option × finance product), not a column of PDFs.
7. **Shade is SHOWN, never stated.** Irradiance heat-map on the 3D roof, sun-path animation, per-panel access. No competitor leads with a percentage.
8. **Left controls / right consequence.** Aurora's storage screen: battery + mode + reserve slider on the left, hour-by-hour flow chart with a "Hide battery" toggle on the right.
9. **Storage value is expressed in HOURS, not kWh** — "Backup hours: Cloudy 49 hours / Sunny 7+ days."
10. **Per-channel section visibility**: every tool lets you hide a section from the live presentation, the web leave-behind, or the PDF — independently.
11. **Acceptance COLLAPSES the chooser.** OpenSolar: after signing, the unchosen options and payment terms disappear; the proposal becomes a record of the choice.
12. **The CTA is a next step, not a signature** — "Review Proposal", "Schedule Consultation", deposit milestone — with e-sign as the terminal state.
13. **Engagement telemetry is sold as a feature**: who opened it, how long they looked.
14. **Homeowners compare on price because nothing explains the delta.** The verbatim ask is *"What am I getting for the extra 2 grand?"*
15. **Say the uncomfortable thing plainly.** Exact make/model beats "premium tier-1 panels"; and homeowners wrongly assume a battery keeps the house on in an outage — without a gateway it does not, and that cost never pays back, so it belongs outside the ROI frame.

## SOLARPRO — WHAT THE CODE ACTUALLY DOES TODAY

Read from source, not assumed. Repo root `C:\Users\Ray\Solarpro Claude\repo`.

**Architecture: SolarPro REBUILDS. The project does NOT become the proposal.**

- `app/api/proposals/route.ts` POST — on "Generate", the server calls `getProjectWithDetails()` and writes the **entire Project object** into `proposals.data_json.project`, plus `pricingSnapshot`, `dbUtilityRate`, `stateCode`, `snapshotAt`. Comment: *"proposals are immutable snapshots."* A proposal is a separate DB row that is a photocopy of the project at one instant.
- `rowToProposal()` explicitly prefers the frozen snapshot: *"Prefer snapshot project (immutable) over live project (may have drifted)"*.
- Once created, **nothing keeps them in agreement.** Grep for `stale|drift|outOfDate` across `app/proposals`, `app/api/proposals`, `lib/proposal`, `components/project/ProposalTab.tsx` returns only comments — **no drift detection exists**. Neither the designer nor the homeowner is ever told the sent proposal no longer matches the design.

**The refresh path exists but is hidden and unguarded.**
- `PATCH /api/proposals/[id]` with `{action:'refresh_snapshot'}` (`app/api/proposals/[id]/route.ts:344-411`) re-pulls the live project + utility rate and overwrites `data_json.project`. This is functionally Enerflo's sync button.
- It is reachable **only** from a kebab overflow menu on the proposals LIST page, labelled "Refresh Data", sandwiched between Rename/Duplicate and Archive/Delete (`app/proposals/page.tsx:164`). It is absent from the proposal view and absent from the project's Proposal tab.
- 🚨 **It has no status guard.** It will happily rewrite the snapshot of an `accepted` / signed proposal, silently changing the numbers the homeowner e-signed against. (Same defect class as the WS-A issued-package re-dating incident.)
- It also does **not** refresh `pricingSnapshot`, so after a refresh the proposal carries live layout/production against frozen pricing — a mixed-vintage document.

**Single financial source of truth — a genuine strength.**
- `lib/proposal/buildCanonicalProposal.ts` (1,005 lines) is the one calculator; the web viewer uses it in 89 places (`cp.*`) and the PDF route calls it too. Comment at `app/proposals/view/[id]/page.tsx:334`: *"ALL financial calculations live in buildCanonicalProposal()."* Supporting truth engines: `utilityTruthEngine`, `incentiveTruthEngine`, `financialNarrativeEngine`, `proposalTruthEngine.ts` (1.97 MB nationwide utility profile registry, net-metering/true-up typed, no name-string matching).

**Three renderers, and one of them is orphaned.**
1. Homeowner web: `app/proposals/view/[id]/page.tsx` — 2,472 lines, React + recharts, **dark theme** (`bg-slate-900`).
2. Homeowner/installer PDF (both download buttons): `lib/proposalPDF.ts` — html2canvas + jsPDF **raster screenshot** of the live DOM, page-packed into ≤12 pages.
3. `GET/POST /api/proposals/[id]/pdf` → `lib/proposal/renderProposalHTML.ts` (963 lines of hand-built light-theme HTML + inline SVG charts) → Puppeteer.
   - 🚨 **Nothing in the UI calls path 3.** Both `handleDownloadPdf` (viewer) and `handleDownloadPDF` (list) import `lib/proposalPDF`. Meanwhile `lib/roadmapRE26.ts:931` asserts *"Download button wired in proposal viewer (handleDownloadPdf...)"* — that claim is false; 963 lines of renderer are API-only.
   - 🚨 Path 3 reads `purchaseMode` from `pricingCfg.purchaseMode` (admin default), whereas the web viewer's `purchaseMode` is homeowner-toggled React state defaulting to `'finance'`. The two paths can disagree on cash-vs-finance for the same proposal.

**What the homeowner actually sees.**
- Sticky header with **Sign & Accept**; `SignatureModal`; bottom CTA *"Legally binding e-signature · No DocuSign needed"*; a 5-step **"What Happens After You Sign"** timeline (step 2 is *Site Survey — "confirm the design"*, i.e. the exact moment drift is created).
- A homeowner-visible **Finance / Cash** toggle (`purchaseMode`, used in 14 render branches). Only ONE loan (`pricingCfg.loanApr`, `loanTermYears`). **No lease, no PPA, no TPO** — just a static marketing line *"$0-Down Lease & PPA Options Available"*.
- **No system options at all.** Grep for `systemOption|proposalOption|goodBetterBest|variant` across the proposal code returns **zero hits**.
- 🚨 **The homeowner never sees the design.** The only site imagery is a Google Static Maps satellite tile at zoom 19 (`app/proposals/view/[id]/page.tsx:831-852`) captioned *"Your Property — system designed for this site"* — **with no panels drawn on it**. Every competitor shows the array.
- Shade is one number: a **TSRF badge** (`{tsrf*100}% · shade analysis applied`, red/amber/green at 0.85/0.95). No heat map, no per-panel access, no sun path. Competitors never lead with a number.
- Genuinely **better than competitors**: the *"How Your Energy Value Is Calculated"* section splits year-1 value into self-consumed (full retail) vs exported, and names the net-metering regime in plain English. Aurora and OpenSolar both show a single blended savings figure. **Protect this.**
- Also present and competitive: first-view email notification to the installer, `?track=1` view counter, share tokens with 30-day expiry, and a `proposal-expiry` cron that emails the rep 3 days before the link dies (idempotent via `reminder_sent_at`, migration 090).

**Mobile.** 20 responsive-breakpoint usages across a 2,472-line homeowner page. Dark theme only, no light mode, no device preview. Competitors author against explicit mobile/tablet/PDF previews.

**Incidental (out of Lane C scope, flagged for the owner):** a Google Maps Static API key is hardcoded as a string literal in client-side source at `app/proposals/view/[id]/page.tsx:836` and is therefore shipped to every homeowner's browser.

## TOP CANDIDATES FOR SOLARPRO

### 1. Drift banner + refresh inside the proposal (the single highest-value item)
- **Build:** a `snapshotAt` vs `project.updated_at` comparison surfaced as an amber strip at the top of the proposal view AND the project's Proposal tab — *"This proposal was built from the design as of 12 Sep. The design has changed since."* — with a **Refresh from design** button that calls the existing `refresh_snapshot` action. Add a status guard so `accepted`/signed proposals refuse the refresh and offer **Create revision** instead. Extend `refresh_snapshot` to re-freeze `pricingSnapshot` so the document is single-vintage.
- **Why it beats what we have:** the mechanism already exists and is correct; it is simply invisible and unguarded. Aurora ships it as one button on the share dialog; Enerflo ships it inside the proposal and calls it the headline of the integration.
- **Bounded:** one comparison, one banner component, one guard clause, one field added to the refresh payload. No new tables.
- **Proof:** change the layout after generating a proposal → banner appears; click refresh → figures move and `snapshotRefreshedAt` advances; sign the proposal → refresh is refused with a revision offer; assert `pricingSnapshot.__version` advances with the project snapshot.

### 2. Send-gated-on-save
- **Build:** disable **Generate / Send** in `ProposalTab` and the share/send-email routes whenever the project has unsaved or newer-than-snapshot design state, with OpenSolar's exact affordance — a disabled button carrying the reason.
- **Why:** it makes the whole class of drift bugs unreachable at the point of origin rather than detected afterwards. It is the cheapest correctness win in the lane.
- **Bounded:** one guard in `POST /api/proposals` and `POST /api/proposals/[id]/send-email`, one disabled state.
- **Proof:** dirty the design, attempt send → 409 with the reason; save → send succeeds.

### 3. Show the array in the proposal
- **Build:** replace the bare satellite tile with a rendered image of the actual layout — panels drawn over the site, produced once at snapshot time and stored with the proposal (so it is immutable with the rest of the snapshot and survives into the raster PDF).
- **Why:** this is the biggest single credibility gap. Every competitor leads with the design; SolarPro leads with a photograph of a roof that could be anyone's. The caption currently asserts *"system designed for this site"* while showing no system.
- **Bounded:** one server-side render at proposal creation + one `<img>`. No live 3D required for v1.
- **Proof:** generate a proposal on a multi-plane roof; the stored image shows the same panel count as `layout.totalPanels`; regenerate after adding panels and confirm the image changes only on refresh.

### 4. One link, N options — with a compare matrix
- **Build:** promote options to a first-class concept: a proposal carries 1–3 design/pricing variants (clone-of-design, each with its own production, BOM and price), a persistent right-rail switcher, and a Compare view laid out as design-option × finance-product (rows: system kW / battery kWh / offset % / **backup capability and hours** / gross / net / monthly). The backup row must state *"no backup without a transfer gateway"* when no gateway/backup switch is in the BOM — the buyer-side source names this as the single most common homeowner misconception, and it must sit outside the ROI frame because it never pays back.
- **Why:** the independent operator named this his single favourite feature — *"no juggling multiple PDFs or multiple links"* — and the buyer-side source names the exact question it answers: *"What am I getting for the extra 2 grand?"* SolarPro currently emits one link per option and has zero option concept in code.
- **Bounded, but the largest item here:** needs a `proposal_options` shape inside `data_json` (no schema migration strictly required) and an option-aware `buildCanonicalProposal` loop. Everything downstream already recomputes from `cp`.
- **Proof:** one proposal link renders 3 options; switching recomputes all 14 `purchaseMode` branches plus production and BOM; the compare table's net cost per option equals each option's own canonical `financial.systemCost`.

### 5. Explain shade the way the competitors do
- **Build:** keep TSRF but demote it. Lead with a per-panel shade visual on the array image (green→amber→red from the `annualShadeFactor` already stored on `layout.panels[]`) and one plain sentence — *"Trees to your south-west cost this design about X% of its annual sunlight; the panels were placed to avoid the worst of it."*
- **Why:** three of four products spend real screen time on an irradiance overlay and call it their trust-builder. A red "TSRF 82.4%" badge on a homeowner document reads as a defect, not as expertise.
- **Bounded:** the data already exists (`panelsShadeDerateComputedPct` is computed at `view/[id]/page.tsx:359-375`); this is a rendering change on top of candidate 3.
- **Proof:** a heavily-shaded test site produces a visibly graded array image whose mean factor equals the computed derate; a clear roof produces a uniform image and the sentence is suppressed.

### 6. Per-channel section visibility + device preview
- **Build:** a section manifest (`cover, overview, production, shade, energy-value, bill-before-after, 25yr, investment, after-you-sign, …`) with three independent toggles per section — live view / web link / PDF — plus desktop/mobile/PDF previews in the authoring UI. Fold the orphaned `renderProposalHTML` decision here: either wire it to a button or delete it, but do not keep two hand-maintained renderers.
- **Why:** Aurora and Solargraf both ship this and reps use it constantly; and it forces the renderer duplication to be resolved rather than drifting further.
- **Bounded:** a manifest + conditional rendering; the section blocks are already tagged `data-block-id` for the PDF packer.
- **Proof:** toggling a section off removes it from the web link and the raster PDF in the same pass; the section list in the manifest matches the `data-block-id` set exactly (a test that also catches the two renderers diverging).
