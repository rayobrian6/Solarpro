# POL-SEC-009 — Password & Authentication Policy

**Document ID:** POL-SEC-009  
**Version:** 1.0  
**Effective Date:** July 2025  
**Review Cadence:** Annual  
**Owner:** Security Lead  
**Approved By:** Leadership  

---

## 1. Purpose

This policy defines the requirements for authentication mechanisms, password management, multi-factor authentication (MFA), and session control across all SolarPro systems. Strong authentication is the primary defense against unauthorized access and is a foundational requirement for SOC 2 (Trust Services Criteria CC6.1) and ISO 27001 (Annex A A.9).

## 2. Scope

This policy applies to:

- SolarPro application accounts (all roles: super_admin, admin, staff, crew_member, homeowner)
- Infrastructure accounts (Vercel, Neon, GitHub, Stripe, Sentry, Google Cloud, Anthropic, OpenAI)
- Developer accounts and tooling access
- Service accounts and API keys
- All personnel: employees, contractors, temporary workers, vendors with system access

## 3. Password Requirements

### 3.1 Application Password Policy

| Requirement | Admin / Staff | Homeowner / Crew |
|-------------|--------------|------------------|
| Minimum length | 14 characters | 12 characters |
| Maximum length | 128 characters | 128 characters |
| Complexity | Must include 3 of 4: uppercase, lowercase, digit, special | Must include 2 of 4: uppercase, lowercase, digit, special |
| Password history | Last 12 passwords cannot be reused | Last 6 passwords cannot be reused |
| Maximum age | 90 days | 365 days |
| Minimum age | 1 day (prevent rapid cycling) | 1 day |
| Account lockout | 5 failed attempts → 30-minute lockout | 10 failed attempts → 30-minute lockout |
| Breached password check | Must not appear in known breach databases | Must not appear in known breach databases |

### 3.2 Infrastructure Password Policy

All infrastructure platform passwords (Vercel, Neon, GitHub, Stripe, Sentry, Google Cloud, Anthropic, OpenAI) must:

- Be at least 16 characters in length
- Be generated by a password manager (not human-created)
- Include uppercase, lowercase, digits, and special characters
- Be unique per platform (no password reuse across services)
- Be rotated every 90 days or immediately upon personnel change
- Be stored exclusively in the approved company password manager

### 3.3 Password Storage

| Requirement | Implementation |
|-------------|---------------|
| Hashing algorithm | bcrypt (cost factor ≥ 12) or argon2id |
| Salt | Auto-generated per hash (bcrypt/argon2 built-in) |
| Plaintext storage | Prohibited under all circumstances |
| Reversible encryption | Prohibited for passwords |
| Transmission | TLS 1.2+ only; HTTP transmission prohibited |
| Logging | Passwords must never appear in logs, error messages, or debug output |

### 3.4 Password Manager

SolarPro mandates the use of an approved password manager for all personnel with access to company systems. The approved password manager must:

- Use zero-knowledge encryption (provider cannot access stored passwords)
- Support MFA for password manager access
- Support secure sharing of credentials among authorized team members
- Generate passwords meeting the requirements above
- Available options: 1Password Business, Bitwarden Business, or Leadership-approved alternative

Personnel must not store passwords in:
- Browser password stores (Chrome, Safari, etc.) — for company credentials
- Plain text files, documents, or spreadsheets
- Sticky notes, whiteboards, or other physical media
- Chat messages, email, or Slack

## 4. Multi-Factor Authentication (MFA)

### 4.1 MFA Enforcement Matrix

| System | MFA Required | Approved Methods | Enforcement |
|--------|-------------|------------------|-------------|
| SolarPro app (admin/staff) | **Mandatory** | TOTP, WebAuthn/FIDO2 | Technical enforcement (no bypass) |
| SolarPro app (homeowner) | Available | TOTP, email OTP | Encouraged but not enforced |
| Vercel | **Mandatory** | Platform-native (GitHub/Google SSO + MFA) | Verified during access review |
| Neon | **Mandatory** | Platform-native | Verified during access review |
| GitHub | **Mandatory** | TOTP, WebAuthn, platform-native | Organization policy enforced |
| Stripe | **Mandatory** | Platform-native (SMS + TOTP) | Verified during access review |
| Sentry | **Mandatory** | Platform-native (Google SSO + MFA) | Verified during access review |
| Google Cloud | **Mandatory** | Google native MFA | Organization policy enforced |
| Anthropic console | **Mandatory** | Platform-native | Verified during access review |
| OpenAI console | **Mandatory** | Platform-native | Verified during access review |

### 4.2 Approved MFA Methods (in order of preference)

1. **WebAuthn / FIDO2 security keys** (YubiKey, Titan Key) — Highest security; resistant to phishing
2. **TOTP** (Google Authenticator, Authy, 1Password TOTP) — Strong security; widely supported
3. **Platform-native MFA** (GitHub, Google, Stripe built-in MFA) — Acceptable when provided by the platform
4. **Hardware security keys + TOTP** — Recommended for super_admin and admin accounts (two separate MFA factors)

### 4.3 Prohibited MFA Methods

- **SMS-based OTP** — Not approved for any system due to SIM-swapping risk
- **Email-based OTP** — Not approved as a primary factor (acceptable as backup for homeowner accounts only)
- **Security questions** — Not considered a valid authentication factor

### 4.4 MFA Recovery

- Recovery codes must be generated at MFA enrollment and stored in the company password manager
- Account recovery requires identity verification by the Security Lead
- Recovery must be completed within 24 hours of request
- MFA must be re-enrolled after recovery (new recovery codes generated)
- All recovery events are audit-logged

## 5. Session Management

### 5.1 Session Duration Limits

| Role | Maximum Session Duration | Idle Timeout | Absolute Timeout |
|------|-------------------------|-------------|------------------|
| super_admin | 8 hours | 30 minutes | 8 hours |
| admin | 8 hours | 30 minutes | 8 hours |
| staff | 8 hours | 30 minutes | 8 hours |
| crew_member | 12 hours | 60 minutes | 12 hours |
| homeowner | 30 days | N/A | 30 days |

### 5.2 Session Security Requirements

- Sessions must be identified by cryptographically random tokens (minimum 256 bits)
- Session tokens must be transmitted only over TLS 1.2+ connections
- Session tokens must be stored in HTTP-only, Secure, SameSite=Strict cookies
- Concurrent sessions for admin/staff roles: maximum 2 active sessions per user
- Session tokens must be invalidated on logout, password change, and MFA enrollment change
- Session token rotation must occur at least every 60 minutes for admin/staff sessions

### 5.3 JWT-Specific Requirements

SolarPro uses JWT (JSON Web Tokens) for authentication:

- JWT signing algorithm: HS256 (enforced, no algorithm negotiation)
- JWT secret: Minimum 256 bits, stored in environment variables, never in code
- JWT expiration: Aligned with session duration limits above
- JWT must include: user ID, role, issued-at, expiration, issuer (solarpro)
- JWT must be validated on every request: signature, expiration, issuer, role
- Timing-safe comparison must be used for JWT signature verification (prevents timing attacks)
- Refresh tokens must be single-use and rotated on each use

## 6. Service Accounts and API Keys

### 6.1 Service Account Requirements

| Requirement | Standard |
|-------------|----------|
| Unique per integration | Each service account serves one purpose only |
| Designated owner | Every service account has a named human owner |
| Minimum permissions | Granted least-privilege access only |
| Key length | Minimum 256 bits for API keys |
| Key format | Cryptographically random; no predictable patterns |
| Storage | Environment variables only; never in source code |
| Rotation | Quarterly (or immediately upon suspected compromise) |
| MFA | Not applicable (automated); compensating controls required |

### 6.2 API Key Management

- All API keys must be provisioned through a documented process
- API keys must be unique per environment (development, staging, production)
- API keys must have expiration dates and be rotated before expiry
- Lost or compromised API keys must be revoked immediately and replaced
- API key usage must be audit-logged (key ID, action, timestamp, source IP)
- API keys must not grant broader permissions than required by the consuming service

### 6.3 Secret Scanning

- GitHub secret scanning must be enabled on all SolarPro repositories
- Pre-commit hooks should prevent committing patterns that look like secrets
- If a secret is committed to the repository: immediately rotate the secret, scan git history, assess blast radius

## 7. Authentication Architecture

### 7.1 Current Authentication Flow

```
User → Login Form → Credentials Submitted (TLS)
  → Server Validates Password (bcrypt/argon2 compare)
  → MFA Challenge (TOTP/WebAuthn)
  → JWT Issued (HS256 signed)
  → Session Cookie Set (HTTP-only, Secure, SameSite)
  → Subsequent Requests: JWT Validated (timing-safe)
```

### 7.2 Required Enhancements for Compliance

| Enhancement | Priority | SOC 2/ISO 27001 Reference |
|-------------|----------|---------------------------|
| MFA enforcement for admin/staff | Critical | CC6.1 / A.9.4.2 |
| Rate limiting on auth endpoints | Critical | CC6.1 / A.9.5.1 |
| Account lockout mechanism | High | CC6.1 / A.9.2.6 |
| Breached password screening | High | CC6.1 / A.9.2.4 |
| Session timeout enforcement | High | CC6.1 / A.9.4.2 |
| Failed login audit logging | High | CC7.2 / A.9.4.3 |
| Concurrent session control | Medium | CC6.1 / A.9.4.2 |
| Password rotation enforcement | Medium | CC6.1 / A.9.2.5 |

## 8. Compliance Verification

### 8.1 Quarterly Authentication Review

The Security Lead must verify:

- [ ] All admin/staff accounts have MFA enabled
- [ ] All infrastructure accounts have MFA enabled
- [ ] No shared accounts exist
- [ ] No expired API keys are active
- [ ] Password policy is technically enforced (not merely documented)
- [ ] Session timeouts are correctly configured per role
- [ ] Breached password screening is operational
- [ ] Account lockout is operational

### 8.2 Annual Authentication Audit

An annual audit must include:

- [ ] Review of all service accounts and their permissions
- [ ] Verification of API key rotation compliance
- [ ] Assessment of JWT implementation security
- [ ] Review of MFA enrollment rates
- [ ] Test of account recovery procedures
- [ ] Verification of password storage security (hashing, salting)
