## §3 — Parallel plan-set generator contained (fail closed)

New authority: `lib/plan-set/legacy-path-guard.ts`.

- `resolveLegacyPathStatus(snapshot)` returns a PASS / permit-ready declaration
  ONLY when `isSnapshotPermitValid(snapshot)` is true — i.e. the snapshot carries a
  real `meta.snapshotId` (`PDS-…`), a `meta.digest` (≥16 hex), and completed
  validators (`permitReadiness.ready === true` with an EMPTY `blockers` list).
  Anything missing/invalid ⇒ the explicit `LEGACY_NOT_FOR_PERMIT` state. Fail closed.
- `LEGACY_PATH_BANNER = "LEGACY PATH — NOT FOR PERMIT / PENDING CANONICAL MIGRATION"`.

The `/api/engineering/plan-set` route consumes NO snapshot, so it calls
`resolveLegacyPathStatus(null)` — structurally forced into the legacy state. The
hardcoded `structuralStatus = 'PASS'` and `overallCompliance: 'PASS'` are gone;
both are now derived from the resolver. Response headers add `X-Permit-Ready:false`
and `X-Plan-Set-Legacy:true`; the JSON body adds `permitReady`, `legacyPath`,
`legacyBanner`.

Visible legacy banner is rendered on the status-bearing sheets:
- **G-1 Cover** (`cover-sheet.ts`, new `legacyBanner` input) — red banner under the header.
- **S-1 Structural** (`structural-sheet.ts`) — banner under header + the green
  "✓ STRUCTURAL PASS" box is replaced by a "LEGACY PATH — NOT FOR PERMIT" box.
- **C-1 Compliance** (`compliance-sheet.ts`) — banner + structural item forced to
  REVIEW + the certification affirmation replaced by a NOT-FOR-PERMIT disclaimer.

Data display on all sheets is unchanged — only the status/banner changes.

Proof: `tests/planset/legacy-path-containment.test.ts` — no-snapshot and every
invalid-snapshot shape resolve to legacy (never PASS); a valid canonical snapshot
is the ONLY path to PASS (gate is real, not always-legacy); the S-1 sheet shows the
banner and NOT "STRUCTURAL PASS" under legacy, and shows PASS only under a canonical
status; the C-1 sheet drops its certification under legacy.

The permanent convert-or-delete decision remains W4; the bypass is neutralized now.

## §4 — RT-MINI 600 lb ASD allowable provenance

`rackingAssembly.ts` now attaches `capacityProvenance` + `structuralAuthorityGaps`
to the record (subtype `RackingAssemblyRecordExt`, part of the record digest). The
600 lb value and existing notes are unchanged (existing W3 test still passes).

IN-REPO EVIDENCE VERIFICATION: **no Roof Tech PE structural letter or datasheet is
archived in this repository.** Searched `docs/`, `public/`, assets, `_tesla_docs`;
only manufacturer marketing detail PNGs exist. ESR-3575 is a flashing /
water-resistance report whose Sec. 5.2 explicitly EXCLUDES structural capacity.
`lib/data/structural/attachment-capacity-basis-research.json` records the 600 lb
value as field-referenced and PROVISIONAL. Therefore:

- `sourceDocument.documentHash = null`, `archivedInRepo = false`,
  `hashNote = "source-document-not-archived …"` — nothing invented.
- `sourceDocument.identity` names the PE letter ("RT-MINI II ASCE 7-10 (KY)") and
  disqualifies ESR-3575 as the source.
- jurisdiction boundary (ASCE 7-10 / KY, not confirmed for project AHJ), exact mount
  model, fastener pattern (2× 5/16" screws, no pilot hole), substrate (15/32"
  sheathing, 2×4 DF-L #2), adjustment factors (implied 1.5 ratio flagged UNVERIFIED),
  ASD-allowable flag, and an assembly-applicability assessment are all recorded.
- **Two BLOCKING gaps** emitted (not applied generically):
  `RACKING-CAPACITY-SOURCE-NOT-ARCHIVED` and `RACKING-CAPACITY-APPLICABILITY-GAP`
  (mixed compatible rail SKU unpinned; jurisdiction unconfirmed).

900 lb "ultimate" exclusion enforced in code: `resolveAsdAllowableLbs(value, basis)`
REFUSES an `ultimate` (or unset) basis as an ASD allowable — returns null + refused.
The 900 lb record is listed in `excludedUltimateRecords`. Genuinely ultimate-basis
mounts (e.g. S-5!) get `ultimateBasisRefusedForAsd = true` + a warning gap.

Proof: `tests/planset/rtmini-capacity-provenance.test.ts`.
