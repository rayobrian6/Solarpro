# v47.422 — MPPT Allocator Spread-Fallback Fix

## Problem
When a single string's NEC design current (Isc × 1.25) exceeds the inverter's
per-MPPT current cap, the allocator's strict candidate filter rejects every
channel (even empty ones). All strings land in `unplacedIds`. Downstream,
`lib/string-generator.ts` line 559 (`?? 0`) collapses them onto channel 0,
causing the MPPT Channel Allocation UI to show CH1 with all strings and
CH2-CH4 empty — hiding the real distribution and overage.

This is a **cross-brand** bug. It will recur for every new inverter we add
whose per-MPPT cap is tight relative to mainstream panels. We fix it once
here so Stages 5.2–5.5 (Solis / Schneider / Victron / OutBack) inherit the
fix for free.

## Fix
1. **Allocator second-pass (forced spread):** After the strict first pass,
   if any strings remain unplaced, run a second pass that places them
   round-robin across channels respecting **only** the parallel-strings cap.
   The current-cap overage is then surfaced per-channel by the existing
   post-placement `MPPT_CURRENT_EXCEEDED` defensive check (bin-level).
   `valid === false` is preserved — we are not silencing the error, we are
   presenting it honestly across channels.

2. **String-generator display:** No line-557 change required. The second
   pass ensures every string has a real channel assignment, so the `?? 0`
   fallback becomes dead code (kept as defense-in-depth).

## Invariants Preserved
- Pure function, no I/O, no input mutation.
- Valid allocations unchanged (second pass only runs when first pass fails).
- Never force-passes: `valid` still becomes `false` on any violation.
- No change to public types, violation codes, or return shape.

## Tests
- Existing 719 tests MUST remain green.
- New tests:
  - Single-string exceeds cap → spread across channels, each channel gets
    one string, per-channel `MPPT_CURRENT_EXCEEDED` emitted with accurate
    overage, `valid === false`.
  - Multi-string exceeds cap (5 strings, 4 channels) → 2+1+1+1 round-robin,
    per-channel current reported correctly.
  - Within-cap case → identical behavior to v47.421 (no regression).
  - Parallel-cap-limited spread → respects parallelCap in second pass.
