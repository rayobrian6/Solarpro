### 1. Health endpoint always 500s: pipeline query references nonexistent published_at column
`repo/app/api/admin/network/health/route.ts:37` · SQL / nonexistent column · area: `api-admin-network`

The pipelineRows query filters `status = 'live' AND claim_count = 0 AND published_at < NOW() - INTERVAL '48 hours'`. - **Fix:** Replace `published_at` with `live_at` (the actual published timestamp), e.g. `AND live_at < NOW() - INTERVAL '48 hours'`. Verify against the schema in migration 062/072.

### 3. 'update' action lets a plain admin set any user's role to super_admin, bypassing the super_admin gate
`repo/app/api/admin/users/route.ts:140` · privilege-escalation · area: `api-admin-projects-users`

In PATCH /api/admin/users the 'set_role' action correctly requires admin.role === 'super_admin' (line 127). Alternatively, strip 'role' from the COALESCE update entirely and force all role changes through 'set_role'.

### 4. Free POST /claim path claims paid marketplace leads with no payment
`repo/app/api/network/opportunities/[id]/claim/route.ts:95` · monetization-bypass · area: `api-marketplace-money`

For network_opportunities (the SolarPro pay-to-claim inventory), POST .../claim takes the network branch (lines 95-148) which, after only an eligibility check, inserts/updates an opportunity_assignments row to status='claimed', stamps claim_amount = asking_price, increments claim_count, and unlocks the homeowner's full address — with NO Stripe charge and no payment_intent_id. Reserve the free-claim path for pre-issued, zero-price offers only.

### 5. Portal bill upload forwards the wrong session cookie, so every homeowner upload fails
`repo/app/api/portal/bill-upload/route.ts:99` · broken-auth-flow · area: `api-auth-account`

The portal route authenticates the homeowner via getPortalSession() (cookie 'solarpro_portal_session'). Either (a) refactor the bill-parsing logic into a shared lib function that both routes import directly (no HTTP self-call), or (b) call /api/bill-upload with a trusted service credential / internal header that the bill-upload route accepts for portal-originated requests, rather than forwarding the homeowner's portal cookie which that endpoint cannot validate.

### 7. NREL residential rate incorrectly divided by 100, persisting a 100x-understated $/kWh rate
`repo/lib/enrichment/utilityEnricher.ts:143` · money-math/wrong-units · area: `lib-proposal-incentive-ops`

enrichFromNREL sets `electricity_rate_kwh: outputs.residential ? parseFloat(outputs.residential) / 100 : statPolicy.avg_rate_kwh`. The NREL Utility Rates API v3 returns `outputs.residential` already in $/kWh (e.g. 0.1369), not cents. The repo's own other consumer of the identical API, lib/utilityDetector.ts lines 119-120, parses `outputs.residential` directly as a $/kWh rate (default '0.13') with NO division. Downstream savings/payback math built on that rate is wildly wrong (savings ~100x too small). - **Trigger:** runEnrichmentOrchestrator / enrichUtility for any opportunity when NREL_API_KEY is configured and NREL returns outputs.residential.
- **Fix:** Remove the `/ 100`: `electricity_rate_kwh: outputs.residential ? parseFloat(outputs.residential) : statPolicy.avg_rate_kwh` (matching utilityDetector.ts). Optionally guard with a sanity range like the 0.05–0.50 bounds used elsewhere.

### 8. generatePayloadIdempotencyKey misuses JSON.stringify replacer arg — all webhook payloads from a platform collapse to the same key, dropping leads
`repo/lib/intake/webhookVerifier.ts:186` · logic/idempotency · area: `lib-intake-db`

generatePayloadIdempotencyKey does `JSON.stringify(payload, Object.keys(payload).sort())`. The second argument of JSON.stringify is a REPLACER ARRAY (a property allowlist), not a key sorter, and it is applied recursively at EVERY nesting level. Since the webhook routes call it as `generatePayloadIdempotencyKey({ platform: 'meta', body })`, the only allowed top-level keys are 'body' and 'platform'; the nested lead object (entry/changes/value/field_data) has keys NOT in that allowlist, so it serializes to `{}`. I verified this at runtime: two completely different Meta lead bodies both produce `{"body":{},"platform":"meta"}` and hash identically. This is the FALLBACK idempotency key used whenever the platform omits a request_id. In app/api/intake/webhook/meta|google|generic the key is inserted into webhook_ingestion_log with `ON CONFLICT (idempotency_key) DO NOTHING`; the first such webhook inserts a row, and EVERY subsequent webhook without a request_id collides, returns `logId=null`, and short-circuits with `{ duplicate_request: true }` (HTTP 200) WITHOUT processing the lead. Trigger: any second+ Meta/Google/generic lead webhook that arrives without a provider request_id. Effect: silent, permanent loss of paid marketplace leads.

- **Trigger:** A second (or later) inbound Meta/Google/generic lead webhook that lacks a platform request_id, so the content-hash fallback path is used.
- **Fix:** Serialize the whole payload deterministically without a replacer array. Use a stable stringify that sorts keys at every level, e.g. a recursive canonicalizer, or at minimum `JSON.stringify(payload)` (drops the sort but preserves content uniqueness). Concretely: replace the body with `const json = stableStringify(payload)` where stableStringify recursively sorts object keys, then hash that. Do NOT pass Object.keys(...) as the second JSON.stringify argument.

### 9. 25-yr projection chart plots per-year energy value as a 'Cumulative Solar Value' line vs a truly cumulative utility line
`repo/lib/proposal/renderProposalHTML.ts:524` · wrong-logic/chart-misrepresentation · area: `lib-proposal-incentive-ops`

In page25YrProjection(), the red line `cumulativeUtility` is built by running-summing `y.utility_cost_without_solar` across all 25 years (genuinely cumulative). The green line is `cumulativeSolar = yearlyFlow.map(y => y.total_energy_value)` — this is the PER-YEAR energy value (self_consumed_value + monthly_export_value + annual_excess_value for a single year, per CanonicalEnergyFlowYear), NOT cumulative. - **Trigger:** Any proposal PDF rendered via renderProposalHTML (the 25-Year Financial Projection page).

### 10. transfer_ownership demotes all super_admins before verifying the new owner exists, can leave a company with no owner
`repo/app/api/admin/companies/route.ts:166` · non-atomic-write · area: `api-admin-projects-users`

The 'transfer_ownership' case runs two separate, non-transactional UPDATEs: first it demotes every super_admin in the company to admin (line 166), then it promotes newOwnerId to super_admin scoped by `id = ${newOwnerId} AND company = ${company}` (line 167). There is no prior check that newOwnerId actually belongs to the company. If newOwnerId is a valid UUID but not a member of that company (wrong id, user in a different company, or a transient failure of the second statement), the second UPDATE matches 0 rows while the first has already demoted all existing owners — leaving the company with zero super_admins and no way to self-recover the owner role.

- **Trigger:** super_admin calls PATCH /api/admin/companies with { company, action:'transfer_ownership', newOwnerId } where newOwnerId is a valid UUID that does not belong to `company` (or the second UPDATE fails after the first succeeds).
- **Fix:** Verify the target user exists in the company first: SELECT 1 FROM users WHERE id = ${newOwnerId} AND company = ${company}; return 404 if absent. Then perform both UPDATEs inside a single transaction so a failed promotion rolls back the demotion.

### 18. Password reset does not invalidate other active sessions despite claiming to
