# v47.429 — Stage 6: Racking Visibility in UI — Plan

## Background

`docs/UPGRADE_ROADMAP_v47.399.md` tracks Stage 6 as:

> **Goal:** Make the racking brands we already have (K2, IronRidge, Unirac, etc.) visible in the UI.
> **Version bump:** v47.406 (originally planned — landing in v47.429).
> **Exit criteria:** You can see and select a racking brand on the engineering page.

## Stage 0 inventory (done during planning)

- `lib/mounting-hardware-db.ts` — **42 systems**, UI-wired via `getAllMountingSystems()`. Used by engineering page brand/model dropdown (lines 7232 and 8520) and `config.mountingId`.
- `lib/racking-database.ts` — **12 systems** across 11 manufacturers (IronRidge, Unirac, Roof Tech, SnapNrack, QuickMount PV, S-5!, K2 Systems, EcoFasten, DPW Solar, Schletter, Esdec). Used only by `structural-engine-v3.ts` and `inventoryAllEquipment.ts`. **NOT reaching UI pickers.**
- `components/engineering/EcosystemPicker.tsx` — inverter-centric; `ResolvedBrandEquipment` has NO racking field.
- Engineering page already has a mounting brand picker. It works, but:
  1. Exit criterion of Stage 6 is already **partially met** (you can select a mounting brand today).
  2. The ecosystem picker shows inverter/battery/gateway/EV but NOT compatible racking, so users don't see the racking story when they apply an ecosystem.

## Scope for v47.429 (kept deliberately tight)

**NOT in scope (Stage 7/8 territory):** merging `racking-database.ts` + `mounting-hardware-db.ts`. Two DBs stay — we just make sure both are reachable and the UI consistently presents one of them.

**In scope:**

### 1. Surface racking in `ResolvedBrandEquipment`
Add `compatibleRacking: MountingSystemSpec[]` to the resolver output. Source: every `MountingSystemSpec` in `mounting-hardware-db.ts` (since that's the UI-canonical set) — return ALL systems by default (racking is brand-agnostic), but flag BrandProfile-preferred ones if the profile declares `recommendedRackingBrands: string[]`.

### 2. Add optional `recommendedRackingBrands?: string[]` to BrandProfile type
Matches the pattern already established by `recommendedBatteryBrands`. Only populate it where we have a clear ecosystem fit (e.g., Tesla + IronRidge, Enphase + Unirac/IronRidge — well-known field pairings). Leave empty for others; dangling tokens will fail the smoke invariant (proven pattern from v47.428).

### 3. Add a "Racking" section to `EcosystemKitPanel`
Matches the visual language of the existing Batteries/Gateways sections. Shows the recommended racking systems for the chosen ecosystem. Falls back to a generic "All major manufacturers compatible" note if the profile has no `recommendedRackingBrands`.

### 4. Racking Ecosystem Smoke Suite (parallel to v47.428's battery smoke)
- Schema integrity (id, manufacturer, category, rail spec if applicable)
- Plausibility (rail length > 0, uplift > 0 where declared)
- No duplicate IDs across `mounting-hardware-db.ts`
- Every `recommendedRackingBrands` token on any BrandProfile resolves to ≥1 system (Global 2)
- Every manufacturer in `MOUNTING_BRANDS` produces ≥1 result when queried
- Audit test locking **all 12** `racking-database.ts` entries against their current values (regression guard)

### 5. Roadmap auto-update
- Flip `stage6-racking-visibility` from planned → done
- Add 4–5 new items for Stage 7/8 follow-ups (consolidation assessment + execution)
- Backfill commit hash once committed

## Exit criteria

1. User opens EcosystemPicker → selects Tesla (or any ecosystem with `recommendedRackingBrands`) → sees a "Racking" section showing compatible systems (NEW).
2. Engineering page mounting dropdown continues to work unchanged (NO regression).
3. Racking Ecosystem Smoke Suite passes (target ~40 CI-blocking tests).
4. Full test suite green: 1630 + ~50 new = ~1680.
5. tsc clean, build 46/46 pages.
6. Roadmap shows stage6-racking-visibility as `done` with commit hash.
