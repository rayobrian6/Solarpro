## 1. Scope Summary

v47.435 ships three largely-independent work-streams. They are listed in priority order and can be phased over one or more release points (v47.435 / v47.435a / v47.436 if separation is cleaner):

1. **Stage 9.2 — Inbound ingest pipeline** (primary scope, BLOCKING for partner integration parity). Turn the 202-logged deliveries into actual `projects` + `Layout` + `project_files` rows.
2. **Stage 9.2b — Handoff JWT minter** (outbound, partner-dependent). Mint HS256 JWTs for the partner's existing `GET /api/handoff/:token` receiver so SolarPro can initiate surveys from a project detail page.
3. **Stage 9.2c — Cross-System Release Signaling (Push)** (outbound, partner-dependent). Emit outbound release events on deploy. Only ships once the partner confirms a receiver URL.

All three share the same outbound-secret-management plumbing and can sensibly be designed together.

## 2. Stage 9.2 — Inbound Ingest Pipeline

(This section is the main v47.435 body. Full design to follow in a subsequent draft. Outline below is a placeholder for the next pass.)

- Fetch full survey payload from partner's `GET /api/surveys/{id}` (blocked on Q2: auth scheme).
- Transform partner fat-payload into SolarPro shapes:
  - `projects` row with `origin='survey'`, `survey_external_id` (idempotency key), `survey_category`, `survey_meta` (JSONB audit trail).
  - `engineeringSeed` populated from partner's structural + roof + electrical fields.
  - `Layout` draft populated from partner's panel plan (if present).
  - `project_files` rows with `status='pending'` for photos (blocked on Q3: photo URL scheme).
- Upsert with idempotency on `(user_id, survey_external_id)`.
- Update `webhook_deliveries.status` from `'verified'` → `'ingested'` on success, `'failed'` with error details on partial failure.
- Partial-failure strategy: create the project row in an `error_state` with a user-visible reason so manual triage is possible.
- Handle Q8 (null `project_id` surveys — walk-in inspections not initiated by handoff).
- Response contract stays 202 Accepted; reason code changes from `INGEST_NOT_IMPLEMENTED_BUT_LOGGED` to either `INGESTED` (success) or `INGEST_FAILED_QUEUED_FOR_RETRY` (recoverable failure path).

## 3. Stage 9.2b — Handoff JWT Minter (Outbound)

(Design outline only — full spec in a subsequent pass.)

- New `POST /api/survey/handoff/mint` endpoint, authenticated as project owner.
- Mints HS256 JWT with claims: `iss='solarpro'`, `sub=user_id`, `project_id`, `jti` (random UUID for replay defence), `iat`, `exp` (short TTL, e.g. 10 min).
- Signed with shared `SOLARPRO_HANDOFF_SECRET` (partner rotates independently).
- Returns `{ token, launchUrl }` where `launchUrl` is the partner's deep-link URL (blocked on Q4: exact URL shape — `/launch?token=...` vs `/new-survey?token=...` vs mobile deep-link scheme).
- Partner's `GET /api/handoff/:token` (already shipped at `github.com/kilby8/site_survey-app@2cc3537f`) consumes the token, verifies, dedupes via `used_handoff_tokens`, and redirects to the survey UI.

## 4. Stage 9.2c — Cross-System Release Signaling (Push)

**Context:** v47.434c shipped pull-based signaling (`GET /api/system/capabilities` + `GET /api/system/release`). The partner can poll these today. This section specifies the push side for when/if we decide ops visibility is better served by proactive notification.

### 4.1 Goal

Emit an HMAC-signed `system.release` event to the partner's webhook receiver whenever SolarPro deploys a new `BUILD_VERSION`, so the partner's ops dashboard can display our current version without polling.

### 4.2 Wire Contract (proposed — subject to partner negotiation)

**Endpoint (partner-side):** TBD — partner must confirm. Candidate: `POST /api/webhooks/solarpro-release`.

**Headers (mirror the inbound survey-complete contract for symmetry and partner familiarity):**

| Header | Format | Notes |
|---|---|---|
| `Content-Type` | `application/json` | |
| `X-Release-Event-Id` | UUID | For partner idempotency + replay defence |
| `X-Release-Timestamp` | ISO-8601 | Matches our v47.434a dual-mode parser |
| `X-Release-Signature` | `sha256=<hex>` | HMAC-SHA256 over `{timestamp}.{rawBody}` |
| `X-Producer-Version` | `vX.Y[z]` | Quick-glance header (body also contains it) |

**Body (envelope v1.0):**

```json
{
  "schemaVersion": "1.0",
  "event": "system.release",
  "event_id": "<uuid>",
  "released_at": "<ISO-8601>",
  "producer": {
    "service": "solarpro",
    "version": "v47.435",
    "buildDate": "2026-04-23"
  },
  "release": {
    "stage": "Stage 9.2",
    "title": "Survey Ingest Pipeline",
    "summary": "<first 500 chars of BUILD_FEATURES[0]>",
    "breakingContractChanges": false
  },
  "capabilitiesEtag": "\"v47.435-abc123def456\"",
  "capabilitiesUrl": "https://solarpro.example.com/api/system/capabilities"
}
```

Key field `breakingContractChanges`: boolean that tells the partner whether they should immediately fetch the capabilities endpoint and re-validate their integration, vs merely logging the new version.

### 4.3 Shared Secret

`PARTNER_RELEASE_WEBHOOK_SECRET` — new env var, mirrors `SURVEY_WEBHOOK_SECRET` on the inbound side. 32+ random bytes, hex-encoded. Partner holds the same secret for HMAC verification. Rotation policy: coordinate via email exchange (no live rotation mechanism in v1).

### 4.4 Delivery Semantics

- **Persistence:** new `system_release_deliveries` table mirroring the shape of `webhook_deliveries`:
  - `id`, `target` (`'partner'`), `event_type` (`'system.release'`), `event_id`, `release_version`, `signature_header`, `timestamp_header`, `raw_body`, `status` (`received|sent|retrying|delivered|failed|abandoned`), `error_message`, `attempts`, `last_attempt_at`, `created_at`, `delivered_at`.
- **Retry schedule:** match the partner's own schedule for symmetry — 1 min, 5 min, 30 min, 2 hr, 12 hr. Max 5 attempts. Abandoned after all retries → `status='abandoned'` + admin alert.
- **Deploy hook wiring:** two candidate triggers (pick one or both):
  1. **Vercel post-deploy webhook** → `POST /api/admin/release/emit` (authenticated via deploy-hook secret) → enqueues `system_release_deliveries` row → background worker picks up → HMAC sign → POST to partner.
  2. **Manual admin trigger** → `POST /api/admin/release/emit` (gated by admin session) → same downstream.
- **Failure-mode UX:** admin page `/admin/release-log` lists recent deliveries with status + retry visibility + manual "re-send" button on abandoned rows.

### 4.5 Non-Goals

- No multi-receiver fan-out in v1 (one partner, one receiver). Schema leaves room for future `target` values.
- No real-time two-way negotiation (e.g. partner acknowledging breaking changes). Push is fire-and-log; partner's response body is recorded but not parsed.
- No "release bundles" for rapid-fire deploys. Each deploy emits one event. If we ship v47.435 and v47.435a within the same hour, the partner receives two events, not one.

### 4.6 Conditions to Ship

All must be true before we build Stage 9.2c:

- [ ] Partner confirms the receiver endpoint URL
- [ ] Partner agrees to HMAC verification using the envelope-spec above (or negotiates deltas)
- [ ] `PARTNER_RELEASE_WEBHOOK_SECRET` generated + exchanged through a secure channel (1Password / age-encrypted env bundle)
- [ ] Partner confirms their ops team wants push vs being satisfied with pull (the pull-based `/api/system/capabilities` may fully cover their need)
- [ ] Deploy-hook mechanism decided (Vercel hook vs manual admin trigger)

### 4.7 Tests (when Stage 9.2c ships)

- Envelope builder unit tests (pure function, deterministic given `BUILD_VERSION` + `BUILD_FEATURES[0]`)
- HMAC signer tests (round-trip: sign → verify locally with same helper)
- Retry-queue worker tests (exponential backoff, max-attempts termination, status transitions)
- End-to-end drift-guard: mock partner receiver, emit a release, assert exactly one delivery row with `status='delivered'`
- Idempotency test: re-emitting the same `event_id` after a failure doesn't produce a duplicate receiver-side row (partner-dedupe responsibility, but we assert we don't double-send on our side)

### 4.8 Implementation Notes

- Signer reuses `lib/survey/verifyWebhookSignature.ts`'s primitive — extract the low-level `computeSignature(timestamp, rawBody, secret)` helper as its own named export so both inbound verification and outbound signing share the same byte-exact implementation.
- Envelope builder lives in `lib/system/releaseEvent.ts` (mirrors `lib/system/capabilities.ts` layout).
- `system_release_deliveries` migration = `migrations/012_system_release_deliveries.sql`.
- No UI surface change beyond the admin log page.

## 5. Cross-Cutting: Shared Secret Management

All three outbound work-streams (9.2b handoff minter, 9.2c release push) introduce new shared secrets. We should decide once:

| Secret | Direction | Current state |
|---|---|---|
| `SURVEY_WEBHOOK_SECRET` | Inbound (partner → us) | Exchanged, live |
| `SOLARPRO_HANDOFF_SECRET` | Outbound (us → partner handoff receiver) | **Not yet exchanged** — partner side consumes; SolarPro side mints |
| `PARTNER_RELEASE_WEBHOOK_SECRET` | Outbound (us → partner release receiver) | **Proposed** — neither side has it yet |

**Recommendation:** exchange all three via a single coordinated email round with 1Password sharing or age-encrypted attachments. Scope a 30-minute ops sync on the partner side for the exchange.
